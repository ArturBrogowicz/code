\section{Analiza stanu wiedzy o najbardziej dotkliwych atakach DDoS}
Globalny rozwój i rosnąca powszechność wykorzystywania architektur chmurowych, połączone z postępem w implementacji sieci o coraz wyższych przepływnościach, są przyczyną intensyfikacji zagrożeń związanych z rozproszonymi atakami odmowy usługi (ang. \textit{Distributed Denial of Service} -- DDoS). Porównanie dziesięciu niezależnych źródeł obserwacji z lat 2019--2023 -- teleskopów sieciowych, honeypotów, punktu wymiany ruchu (IXP) oraz danych dostawców komercyjnych -- wykazało trend wzrostowy ataków bezpośrednich (ang. \textit{direct-path}) w czterech z pięciu obserwatoriów. Jednocześnie poszczególne źródła istotnie się różnią: każdy punkt pomiarowy obserwuje inny wycinek populacji ataków, a raporty branżowe sygnalizują wzrost liczby ataków w warstwie aplikacyjnej \cite{hiesgen2024age}. Ewolucja technik wykorzystywanych przez atakujących również postępuje: obserwowane jest odejście od prostych prób wysycenia pasma sieciowego na rzecz wielowarstwowych wektorów ataków, operujących na asymetrii zasobów oraz uderzeniach wymierzonych w specyficzną logikę warstwy aplikacyjnej. Uzasadnia to badanie metod detekcji opartych na uczeniu maszynowym, ocenianych jednak zawsze względem prostszych, deterministycznych punktów odniesienia (podrozdział~\ref{sec:metodyka}).

\subsection{Taksonomia współczesnych wektorów DDoS}\label{sec:taksonomia}
Atak odmowy usługi polega na wyczerpaniu skończonego zasobu, od którego zależy dostępność usługi: przepustowości łącza, pamięci stanu w urządzeniach i systemie operacyjnym albo zasobów przetwarzania aplikacji \cite{rfc4732}. Na potrzeby dalszej analizy wyróżniono pięć klas wektorów ataków, zestawionych w tabeli~\ref{tab:taksonomia}. Ataki wolumetryczne bezpośrednie wysycają łącze lub stos sieciowy dużą liczbą pakietów wysyłanych wprost z węzłów botnetu. Ataki odbiciowo-wzmacniające wykorzystują sfałszowany adres źródłowy i niezabezpieczone serwery pośredniczące, np. otwarte resolwery DNS \cite{nawrocki2021far} lub urządzenia pośredniczące (ang. \textit{middleboxes}) odpowiadające na pojedyncze segmenty TCP \cite{bock2021weaponizing}. Ataki na stan protokołu wyczerpują struktury przechowujące połączenia półotwarte, jak w przypadku ataku SYN flood \cite{rfc4987} czy zalewania pakietami inicjującymi połączenia w protokole QUIC \cite{nawrocki2021quicsand}. Asymetryczne ataki warstwy aplikacyjnej wymuszają na serwerze kosztowne przetwarzanie przy niewielkim nakładzie po stronie atakującego, czego przykładem jest HTTP/2 Rapid Reset \cite{pardue2023rapidreset}. Ostatnią klasę stanowią ataki typu \textit{low-and-slow}, które przy minimalnym wolumenie ruchu utrzymują otwarte połączenia i blokują pule zasobów serwera \cite{sikora2021generator,sood2023slowtrack,tripathi2024delays}.

\subsection{Ataki wolumetryczne i sieciowe (L3 i L4)}
Ataki realizowane w warstwie sieciowej (L3) oraz transportowej (L4) modelu referencyjnego ISO/OSI stanowią podstawowy, lecz wciąż intensywnie rozwijany rdzeń operacji DDoS. Ich bezpośrednim celem jest wyczerpanie dostępnej przepustowości łączy telekomunikacyjnych prowadzących do atakowanej maszyny lub całkowite wysycenie skończonych zasobów sprzętowych urządzeń brzegowych, takich jak:
\begin{itemize}
    \item tablice stanów w zaporach sieciowych (ang. firewalls),
    \item bufory interfejsów routerów rdzeniowych,
    \item procesory sieciowe w urządzeniach takich jak routery, switche,
\end{itemize}
Skuteczność tych wektorów ataku wynika z generowania gigantycznego wolumenu ruchu sieciowego, często przy użyciu rozproszonych sieci przejętych urządzeń - botnetów, które wykorzystują architektoniczne właściwości protokołów, takie jak bezstanowość UDP czy mechanikę alokacji pamięci i rezerwacji zasobów przy zestawianiu sesji TCP. Mitygacja tego typu zagrożeń wymaga implementacji zaawansowanych strategii inżynierii ruchu, w tym technik detekcji poza pasmem (ang. out-of-band) oraz infrastruktury o ogromnej przepustowości.
\subsubsection{SYN flood}
Atak typu SYN flood jest jednym z najbardziej klasycznych i fundamentalnych ataków, realizowany w warstwie transportowej L4, bezpośrednio wykorzystuje specyfikację protokołu Transmission Control Protocol - TCP. Aby w pełni zrozumieć działanie tego ataku, należy odnieść się do trójetapowego procesu nawiązywania połączenia (ang. three-way handshake), który w tym protokole jest wymagany do zainicjowania sesji komunikacyjnej między maszynami przez sieć \cite{rfc9293}. W typowych warunkach klient rozpoczyna nawiązywanie połączenia wysyłając do serwera segment TCP z ustawioną flagą SYN -Synchronize oraz wygenerowanym numerem sekwencyjnym. Po odebraniu takiego segmentu serwer docelowy alokuje odpowiednie zasoby w pamięci operacyjnej systemu, tworzony jest tzw. wpis w kolejce połączeń oczekujących, znanej jako SYN backlog queue. Następnie serwer docelowy odpowiada klientowi segmentem zawierającym flagi SYN i ACK (Acknowledgment). Segment ten zawiera również potwierdzenie odebranego numeru sekwencyjnego (w postaci zinkrementowania jego wartości go o 1) oraz nowy numer sekwencyjny wygenerowany przez serwer. W tym momencie połączenie na serwerze przechodzi w stan na wpół otwarty (ang. half-open connection). Ostatnim etapem jest odesłanie przez klienta finalnego segmentu ACK wraz z zinkrementowanymi wartościami numeru sekwencyjnego i potwierdzenia, po którego odebraniu serwer w pełni zestawia połączenie, zmieniając jego stan na ESTABLISHED.

Istotą ataku SYN flood jest masowe generowanie segmentów SYN, w których adresy źródłowe IP są fałszowane (ang. IP spoofing). Serwer ofiary, postępując zgodnie ze specyfikacją protokołu TCP, dla każdego z tych sfałszowanych żądań alokuje cenne zasoby w kolejce backlog i odsyła segment SYN$+$ACK pod wcześniej otrzymany adres IP, po czym przechodzi w stan oczekiwania. Oczekiwany finalny segment ACK od złośliwego klienta nigdy nie nadchodzi, co powoduje, że serwer utrzymuje te na wpół otwarte połączenia aż do momentu upłynięcia określonego limitu czasu (ang. timeout). Ze względu na skończoną wielkość kolejki połączeń oczekujących, ciągły napływ sfałszowanych segmentów SYN prowadzi do jej szybkiego przepełnienia. W konsekwencji system operacyjny ofiary zaczyna odrzucać nowe żądania nawiązania połączenia od prawdziwych użytkowników, co skutkuje odmową dostępu do usługi \cite{rfc4987}.

W ramach przeciwdziałania temu atakowi bez konieczności nieustannej rozbudowy zasobów sprzętowych serwera opracowano mechanizm ciasteczek SYN (ang. \textit{SYN cookies}), którego koncepcję opisał Daniel J. Bernstein \cite{rfc4987}. Polega ona na rezygnacji z alokacji zasobów na serwerze po odebraniu segmentu SYN -- nie jest tworzony wpis w kolejce backlog. Zamiast tego serwer generuje wartość kryptograficzną, która jest odsyłana do klienta jako początkowy numer sekwencyjny w segmencie SYN$+$ACK. W konsekwencji następuje przeniesienie stanu połączenia z pamięci serwera do samego pakietu sieciowego. W systemie Linux mechanizm ten jest wykorzystywany dopiero wtedy, gdy kolejka połączeń półotwartych danego gniazda zostaje przepełniona (parametr \texttt{net.ipv4.tcp\_syncookies}, domyślnie równy 1) \cite{kernel_ipsysctl}.

Ciasteczko ma rozmiar 32 bitów, a jego struktura w klasycznym schemacie składa się z poniższych elementów \cite{rfc4987}:
\begin{itemize}
    \item 5 bitów licznika czasu -- wartości modulo 32 licznika zwiększanego co 64 sekundy, co ogranicza możliwość ataków powtórzeniowych,
    \item 3 bity reprezentujące zakodowaną wartość maksymalnej długości segmentu (Maximum Segment Size) zbliżoną do zadeklarowanej przez klienta w pierwotnym żądaniu,
    \item 24 bity przyciętego skrótu kryptograficznego obliczanego funkcją skrótu na podstawie następujących parametrów połączenia:
    \begin{itemize}
        \item Adres IP klienta
        \item Adres IP serwera
        \item Port klienta
        \item Port serwera
        \item Czas t
        \item Klucz znany wyłącznie serwerowi generowany losowo przy starcie systemu
    \end{itemize}
\end{itemize}
Wartość ciasteczka C można zapisać następująco:
$$C = \text{Timestamp} \parallel \text{MSS}_{index} \parallel \text{Hash}(IP_{src}, IP_{dst}, P_{src}, P_{dst}, \text{Timestamp}, K_{secret})$$
gdzie operator $\parallel$ oznacza konkatenację bitową, a $K_{secret}$ jest tajnym kluczem serwera. W opisie Bernsteina tak wyznaczona wartość jest dodatkowo łączona operacją XOR z początkowym numerem sekwencyjnym klienta \cite{rfc4987}.

W przypadku autentycznego żądania SYN klienta, po odebraniu SYN$+$ACK klient odpowie finalnym segmentem ACK w którym numer potwierdzenia (ang. Acknowledgment Number) będzie równy wartości otrzymanego ciasteczka powiększonej o jeden. Po odebraniu tego segmentu serwer dekoduje numer potwierdzenia, weryfikuje poprawność 24-bitowego skrótu kryptograficznego oraz odtwarza pierwotną wartość MSS. Zasoby w pamięci serwera rezerwowane są zatem wyłącznie dla połączeń, które pomyślnie przeszły weryfikację kryptograficzną, co sprawia, że atak SYN flood oparty na fałszowaniu IP staje się nieskuteczny - nie dochodzi do wyczerpania pamięci po stronie serwera.

Analizując ten mechanizm należy jednak wspomnieć również o jego wadach. W oryginalnej implementacji ciasteczek SYN kodowanie informacji na 32 bitach uniemożliwia zapisanie ważnych opcji TCP, które standardowo są negocjowane w segmencie SYN np. skalowanie okna (ang. window scaling) czy SACK dla niestabilnych łącz; wyłączenie skalowania okna jest wskazywane jako największy koszt stosowania tego mechanizmu \cite{rfc4987}. Obecny jest również narzut obliczeniowy obciążający dodatkowo jednostkę CPU, wynikający z obliczania kryptograficznego skrótu dla każdego segmentu SYN.

Aby zniwelować problem utraty opcjonalnych parametrów połączenia, współczesne implementacje m.in. jądro systemu Linux wprowadzają rozwiązanie polegające na wykorzystaniu opcji znaczników czasu protokołu TCP (ang. TCP Timestamps), zdefiniowanej obecnie w RFC 7323 \cite{rfc7323}. Mechanizm znaczników czasu opiera się na tym, że host wysyłający segment umieszcza w nim swój aktualny czas w polu TSval (Timestamp Value), a odbiorca w odpowiedzi ma obowiązek odesłać tę samą wartość w polu TSecr (Timestamp Echo Reply), nie analizując jej zawartości.

W sytuacji, gdy serwer znajduje się pod atakiem SYN Flood i są aktywne ciasteczka SYN, serwer sprawdza czy klient w żądaniu SYN zadeklarował obsługę opcji Timestamps. Jeśli tak, serwer nie zapisuje w swoim segmencie SYN$+$ACK rzeczywistego czasu. Zamiast tego modyfikuje 32-bitowe pole TSval, w którym koduje brakujące parametry na podstawie wartości wskazanych w pierwszym segmencie SYN od klienta. Struktura tego zmodyfikowanego znacznika czasu w systemie Linux przedstawia się następująco \cite{linux_syncookies}:
\begin{itemize}
\item Najbardziej znaczące 26 bitów: dostosowany rzeczywisty znacznik czasu, pozwala on na zachowanie zgodności z mechanizmem PAWS (Protection Against Wrapped Sequences).
\item 1 bit: flaga obsługi ECN (Explicit Congestion Notification).
\item 1 bit: flaga obsługi SACK (Selective Acknowledgment).
\item Najmniej znaczące 4 bity: zadeklarowana przez klienta wartość skalowania okna (Window Scaling), podawany jako przesunięcie bitowe (potęga liczby 2 w zakresie od 0 do 14).
\end{itemize}
Gdy autentyczny klient odsyła finalny segment ACK, bezpośrednio jest kopiowana wartość z TSval serwera do własnego pola TSecr. Serwer, po pomyślnej weryfikacji głównego 32-bitowego ciasteczka SYN, wyodrębnia za pomocą masek bitowych informacje zakodowane w TSecr. Dzięki temu procesowi serwer odzyskuje wszystkie niezbędne parametry, co pozwala na ostateczne ustanowienie w pełni zoptymalizowanego połączenia bez konieczności alokowania pamięci dla stanów na wpół otwartych.
\subsubsection{UDP flood}
W tym ataku wykorzystywany jest bezstanowy protokół transportowy UDP oparty na datagramach. W przeciwieństwie do połączeniowego protokołu TCP, nie wymaga on wymiany komunikatów inicjujących ani potwierdzania odbioru poszczególnych pakietów przez strony komunikacji, co czyni go idealnym narzędziem w rękach napastników dążących do wygenerowania gigantycznego wolumenu danych przy absolutnie minimalnym nakładzie pracy oraz mocy obliczeniowej po stronie kontrolowanego botnetu. Atak UDP flood wykorzystuje znaczącą asymetrię, polegając na zasypywaniu systemu docelowego masową liczbą stosunkowo małych datagramów UDP, najczęściej ze sfałszowanymi adresami źródłowymi IP, które są kierowane na całkowicie losowe porty urządzenia ofiary.

Problematyczny jest również fakt, iż kiedy system operacyjny stacji docelowej, routera lub urządzenia brzegowego odbiera datagram UDP, standardowa procedura obsługi stosu sieciowego wymaga sprawdzenia, czy do wskazanego portu docelowego przypisana jest jakakolwiek aktywna usługa, która nasłuchuje połączenia (ang. listening state). W przypadku ataku skierowanego na losowe numery portów, prawdopodobieństwo trafienia na aktywną usługę jest znikome. W takiej sytuacji, zgodnie ze standardami zachowania w sieci IP, urządzenie docelowe jest zobligowane do wygenerowania i odesłania komunikatu błędu ICMP Destination Unreachable pod adres źródłowy wskazany w złośliwym pakiecie. Ten proces oddziałuje w sposób zdecydowanie negatywny na wydajność systemu serwera na dwóch płaszczyznach. Po pierwsze, interfejsy sieciowe ofiary zapychane są ogromną liczbą nadchodzących datagramów. Po drugie, zasoby jednostki CPU są wykorzystywane do nieustannej weryfikacji tablicy portów i generowania pakietów ICMP.

W związku z bezstanowością protokołu UDP odróżnienie pakietów złośliwych od legalnego ruchu aplikacyjnego za pomocą tradycyjnych zapór sieciowych czy systemów IPS jest trudne, a głęboka inspekcja każdego pakietu (ang. Deep Packet Inspection) przy atakach o dużym wolumenie jest kosztowna obliczeniowo. Jednocześnie zalewanie pakietami UDP pozostaje według zgodnych raportów branżowych dominującą formą ataków wolumetrycznych \cite{hiesgen2024age}.

Współczesne rozwiązania kładą nacisk na analizę przepływów (ang. flow-based detection) oraz architekturę poza głównym pasmem (ang. out-of-band), gdzie urządzenie monitorujące wykonuje kopię ruchu sieciowego i wysyła ją do systemu analitycznego. Analiza przepływów polega na ekstrakcji kluczowych cech pakietów i grupowaniu ich w ramach przepływów. W standardach NetFlow v9 \cite{rfc3954} oraz IPFIX \cite{rfc7011} przepływ identyfikowany jest zwykle przez następujące parametry \label{Netflow}:
\begin{itemize}
    \item źródłowy adres IP,
    \item docelowy adres IP,
    \item źródłowy numer portu,
    \item docelowy numer portu,
    \item protokół,
\end{itemize}
Następnie analizowane są statystyki opisujące komunikację: liczba pakietów na sekundę (pps) i bitów na sekundę (bps) oraz rozkład wielkości pakietów. Telemetria przepływów jest zwykle próbkowana, co ogranicza widoczność ataków. Przykładowo, analiza ruchu dużego europejskiego punktu wymiany ruchu (IXP), próbkowanego w proporcji 1:16\,000, łączyła test udziału podejrzanych zapytań DNS z minimalną liczbą próbek dla danego celu; 96\% ataków wykrytych w ten sposób było niewidocznych dla rozbudowanej platformy honeypotów, a próg liczby próbek decydował o kompromisie między widocznością ataków a liczbą fałszywych alarmów \cite{nawrocki2021far}. Reakcja na wykryty atak może polegać na propagacji reguł filtrowania protokołem BGP FlowSpec \cite{rfc8955} lub na przekierowaniu ruchu do centrów oczyszczania (ang. \textit{scrubbing centers}), co omówiono w podrozdziale~\ref{sec:umiejscowienie}.
\subsubsection{Ataki odbiciowo-wzmacniające (DNS i TCP)}
Atak DNS Amplification bazuje na zjawisku odbicia (ang. reflection) oraz zjawisku wzmocnienia (ang. amplification). Odbicie polega na skierowaniu odpowiedzi serwera do ofiary poprzez sfałszowanie źródłowego adresu IP w pierwotnym zapytaniu wysyłanym przez atakującego. Wzmocnienie wynika z uzyskania nieproporcjonalnie większej odpowiedzi do maszyny ofiary niż rozmiar wysyłanego pierwotnie żądania. Jest to jeden z najbardziej skutecznych ataków wolumetrycznych, wykorzystujący dysproporcję w konsumpcji przepustowości pomiędzy maszyną inicjującą a infrastrukturą ofiary, eksploatując fundamentalne właściwości protokołu Systemu Nazw Domenowych (DNS). W szczególności podatne są otwarte serwery rekursywne (ang. open resolvers), które odpowiadają na zapytania od dowolnego adresu w sieci publicznej \cite{rfc5358}.

Atak DNS Amplification można opisać w poniższych krokach \cite{nawrocki2021far}:
\begin{enumerate}
    \item Host należący do botnetu generuje datagram UDP z zapytaniem DNS ze sfałszowanym źródłowym adresem IP w nagłówku protokołu IP, wstawiony jest adres IP hosta ofiary.
    \item Zapytanie jest zbudowane w taki sposób, aby uzyskać odpowiedź z serwera DNS o maksymalnym rozmiarze. Wykorzystuje się w tym celu nazwy, dla których odpowiedzi są szczególnie duże, np. domeny podpisane DNSSEC \cite{nawrocki2021far}, oraz typy zapytań takie jak ANY, zwracające wszystkie rekordy danej nazwy; od 2019 roku serwery mogą jednak odpowiadać na zapytania ANY odpowiedzią o minimalnym rozmiarze \cite{rfc8482}. Kluczowe jest tu również wykorzystanie mechanizmu EDNS(0) (ang. \textit{Extension Mechanisms for DNS}), który pozwala na zwiększenie limitu wielkości odpowiedzi UDP ponad klasyczne 512 bajtów, np. do 4096 bajtów \cite{rfc6891}.
    \item Podatny serwer DNS traktuje zapytanie jako autentyczne, ponieważ podstawowy protokół DNS przesyłany przez UDP nie uwierzytelnia nadawcy, i przygotowuje pakiet odpowiedzi o rozmiarze wielokrotnie większym od rozmiaru zapytania.
    \item Wielokrotnie powiększona odpowiedź jest odsyłana pod sfałszowany adres źródłowy. W efekcie ofiara ataku otrzymuje lawinę nieżądanych danych, co w konsekwencji prowadzi do wysycenia jej brzegowych punktów styku z Internetem i niedostępności usługi.
\end{enumerate}

Odbicie i wzmocnienie nie są ograniczone do protokołów bezpołączeniowych. Bock i in. wykazali, że urządzenia pośredniczące, np. systemy cenzury lub zapory korporacyjne, wstrzykują odpowiedzi (np. strony blokady) w reakcji na pojedyncze segmenty TCP, bez uprzedniego uzgodnienia połączenia; w skanowaniu przestrzeni adresowej IPv4 zidentyfikowano 386\,187 adresów zapewniających co najmniej 100-krotne wzmocnienie \cite{bock2021weaponizing}. Z perspektywy obrony na poziomie hosta istotna jest konsekwencja wspólna dla wszystkich ataków odbiciowych: źródłami ruchu widzianymi przez ofiarę są reflektory, a nie atakujący, więc blokowanie adresów źródłowych odcina infrastrukturę pośredniczącą, nie eliminując źródła ataku \cite{nawrocki2021far,bock2021weaponizing}.

Mitygacja ataków amplifikacyjnych odbywa się na wielu płaszczyznach. Po stronie dostawców usług internetowych (ang. Internet Service Provider) stosuje się filtrowanie wejściowe (ang. Ingress Filtering), polegające na odrzucaniu pakietów opuszczających ich infrastrukturę, których źródłowe adresy IP nie należą do zarządzanej przez nich przestrzeni adresowej, co bezpośrednio uniemożliwia fałszowanie adresów \cite{rfc2827}. Operatorzy serwerów DNS ograniczają rekursję do zaufanych klientów \cite{rfc5358} oraz stosują limity szybkości odpowiedzi (ang. Response Rate Limiting), które ograniczają liczbę jednakowych odpowiedzi odsyłanych do pojedynczego docelowego adresu IP w jednostce czasu. W skali produkcyjnej wolumen odbitego ruchu rozprasza się w architekturach anycast \cite{rfc4786,rizvi2022anycast}, omówionych w podrozdziale~\ref{sec:umiejscowienie}.
\subsubsection{Ataki wielocelowe (Carpet Bombing)}
Atak typu \textit{Carpet Bombing} stanowi wariant wolumetrycznych wektorów DDoS w warstwach L3 i L4, w którym złośliwy ruch jest celowo rozpraszany w celu ominięcia mechanizmów detekcyjnych. Klasyczne ataki DDoS koncentrują ruch na pojedynczym docelowym adresie IP, co umożliwia mitygację za pomocą statycznych limitów przepustowości przypisanych do konkretnego hosta. W ataku \textit{Carpet Bombing} botnet równomiernie rozdziela ruch na całe bloki adresowe CIDR w ramach wspólnych prefiksów trasowania BGP. Przykładowo, atak o łącznej przepustowości 200 Gbps, równomiernie rozłożony na 2000 docelowych adresów IP, generuje obciążenie rzędu zaledwie 100 Mbps dla każdego pojedynczego hosta. Dla lokalnych zapór sieciowych i statycznych filtrów taki przyrost ruchu bywa nieodróżnialny od standardowych fluktuacji, natomiast w punktach agregacji, takich jak routery krawędziowe i łącza dystrybucyjne w sieci operatora, kumuluje się pełna skala przepływu 200 Gbps. Rozproszenie utrudnia również pomiar: zdarzenia tego typu muszą być agregowane z obserwacji wielu czujników, ponieważ pojedynczy czujnik może ich w ogóle nie zauważyć \cite{hiesgen2024age}.

Analiza strumieniowa telemetrii przepływów (NetFlow, IPFIX \cite{rfc7011}, sFlow), korelowana z informacjami o trasach BGP, pozwala mapować źródła ruchu na systemy autonomiczne (ASN) i wyznaczać dynamiczne linie bazowe dla obsługiwanego ruchu. Często proponowanym sygnałem detekcji jest entropia rozkładu adresów, jednak jej skuteczność zależy od udziału ataku w ruchu: detektor znormalizowanej entropii zaimplementowany bezpośrednio w płaszczyźnie danych przełącznika P4 generował fałszywe alarmy w 8\% interwałów bez ataku, a atak stanowiący 5\% ruchu wykrywał w 36\% interwałów \cite{ding2021tracking}. Ataki rozproszone na wiele celów pozostają zatem trudne do odróżnienia od naturalnych fluktuacji ruchu.

W przypadku klasycznych ataków wolumetrycznych kierowanych na pojedynczy adres IP, operatorzy powszechnie stosowali metodę RTBH (ang. Remotely Triggered Black Hole). Mechanizm ten polega na rozgłoszeniu w sieci BGP atakowanego prefiksu z dedykowanym atrybutem społeczności, najczęściej oznaczanym wartością 666 \cite{rfc7999}. Powoduje to wymuszenie na routerach brzegowych bezwarunkowego przekierowania całego ruchu skierowanego na dany adres do interfejsu zerowego null0. O ile RTBH z powodzeniem zapobiega saturacji łączy operatora, o tyle jego użycie skutkuje całkowitym odcięciem atakowanego hosta od legalnego ruchu, co oznacza zrealizowanie celu atakującego. Zastosowanie mechanizmu RTBH do całej podsieci podczas ataku Carpet Bombing przyniosłoby katastrofalne skutki, prowadząc do masowej niedostępności usług dla wszystkich klientów w danej puli adresowej.

Rozwiązaniem jest wdrożenie mechanizmu BGP FlowSpec (ang. BGP Flow Specifications), ustandaryzowanego w dokumencie RFC 8955, zastępującym wcześniejszy RFC 5575 \cite{rfc8955}. Technologia ta pozwala rozproszonej architekturze sieciowej na odejście od binarnych blokad całych adresów IP na rzecz propagowania reguł i sygnatur ataku. Filtry FlowSpec mogą uwzględniać kombinacje takich parametrów jak:
\begin{itemize}
    \item port źródłowy,
    \item port docelowy,
    \item rozmiar nagłówka,
    \item typ protokołu warstwy transportowej - TCP/UDP,
    \item typ fragmentacji pakietu.
\end{itemize}
Informacje te są propagowane w szkieletowej sieci operatorskiej poprzez komunikaty \textit{UPDATE} jako atrybut \textit{FLOW\_SPEC\_NLRI} (ang. Network Layer Reachability Information). Towarzyszą im akcje decyzyjne zdefiniowane w społecznościach rozszerzonych (ang. Extended Communities) w obrębie instancji VRF (ang. Virtual Routing and Forwarding). Dzięki orkiestracji polityk narzędziami analitycznymi, routery brzegowe odrzucają wyłącznie złośliwe pakiety należące do wektora ataku, zachowując pełną dostępność usług dla pożądanego ruchu.

\subsection{Asymetryczne ataki w warstwie aplikacyjnej (L7)}
Ataki w warstwie aplikacyjnej modelu ISO/OSI (L7), w przeciwieństwie do wcześniej omówionych metod wolumetrycznych, nie dążą do wysycenia przepustowości pasma telekomunikacyjnego, lecz do asymetrycznego wyczerpania ograniczonych zasobów przetwarzania po stronie samego systemu operacyjnego lub serwera aplikacji, takich jak:
\begin{itemize}
    \item pule dostępnych połączeń,
    \item wątki robocze procesora,
    \item dostępna pamięć alokowana do utrzymywania sesji użytkowników.
\end{itemize}
W tej grupie należy rozróżnić dwie rodziny. Ataki kosztowne obliczeniowo, np. zalewanie żądaniami HTTP czy HTTP/2 Rapid Reset, generują dużą liczbę żądań, z których każde wymaga od serwera nieproporcjonalnie dużej pracy. Ataki typu \textit{low-and-slow} działają odwrotnie: przy minimalnym wolumenie ruchu utrzymują otwarte, technicznie poprawne połączenia i w ten sposób blokują pule zasobów serwera. Ze względu na niewielkie przepływy danych przypominają one legalnych użytkowników korzystających z wolnego łącza internetowego \cite{sikora2021generator}, dlatego podstawowe metody detekcji oparte na sygnaturach i progach wolumenu nie spełniają skutecznie swojej roli.
\subsubsection{Ataki typu low-and-slow: mechanizm i zależność od architektury serwera}
Wspólnym mechanizmem ataków \textit{low-and-slow} jest wysyłanie niekompletnych żądań HTTP lub bardzo powolny odbiór odpowiedzi, przy czym kolejne fragmenty danych przychodzą tuż przed upływem limitu czasu oczekiwania serwera \cite{sikora2021generator}. Skuteczność takiego ataku zależy w dużym stopniu od architektury i konfiguracji serwera. Sikora i in. przetestowali jedenaście wariantów powolnych ataków na protokoły HTTP/1.1 i HTTP/2 wobec serwerów Apache, Nginx, lighttpd oraz IIS w konfiguracjach domyślnych, uznając atak za skuteczny, jeżeli legalny klient obserwował nieprzerwaną niedostępność usługi dłuższą niż 6 sekund. Serwer Apache~2.4.17 uległ wszystkim jedenastu atakom, podczas gdy Nginx~1.14.0 -- jedynie dwóm (Slow Read i Slowcomm); ataki Slowloris i Slow POST były wobec niego nieskuteczne ze względu na architekturę sterowaną zdarzeniami \cite{sikora2021generator}. Równocześnie wiele serwerów w Internecie toleruje niekompletne żądania przez długi czas: w badaniu serwerów obsługujących HTTP/2 około połowa z nich utrzymywała połączenie z niekompletnym żądaniem jednego z badanych typów dłużej niż 360 sekund \cite{tripathi2024delays}.

Z tych właściwości wynika podstawowa trudność detekcji. Proste reguły wykrywające atak na podstawie liczby takich połączeń w zadanym czasie można łatwo ominąć \cite{sood2023slowtrack}. Sood i Hubballi wykazali, że detektor oparty wyłącznie na liczbie niekompletnych żądań tracił w ich eksperymentach blisko 10\% czułości w porównaniu z regułą łączącą osiem parametrów behawioralnych serwera \cite{sood2023slowtrack}. Motywuje to badanie architektury dwupłaszczyznowej, w której deterministyczne heurystyki stanu połączeń współpracują z modelem uczonym na sekwencjach zdarzeń (podrozdział~\ref{sec:ml}).
\subsubsection{SlowLoris}
Atak Slowloris, nazywany również Slow GET lub Slow Header, wykorzystuje mechanizm protokołu HTTP, konkretnie znacznik podwójnego załamania linii "\verb|\r\n\r\n|", który sygnalizuje serwerowi zakończenie nagłówków żądania \cite{sikora2021generator}. Stał się wzorcem klasy ataków skierowanych na serwery WWW, które posiadają granicę maksymalnej liczby równolegle obsługiwanych klientów. Atak typu SlowLoris jest realizowany w następujących krokach \cite{sikora2021generator}:
\begin{enumerate}
    \item Atakujący otwiera wiele (tysiące) prawidłowych połączeń TCP do serwera docelowego, a następnie rozpoczyna wysyłanie spreparowanych, niepełnych nagłówków żądania HTTP, w których celowo pomija końcowy ciąg "\verb|\r\n\r\n|".
    \item W serwerach przydzielających osobny wątek lub proces do każdego połączenia każde z przychodzących żądań zajmuje jeden z ograniczonej puli wątków, ponieważ żądania wysyłane przez atakującego są poprawnie zbudowane. Serwery sterowane zdarzeniami, takie jak Nginx, są na ten wektor znacznie odporniejsze \cite{sikora2021generator}.
    \item Atakujący nie pozwala serwerowi również na zerwanie połączenia z powodu bezczynności - sesje w których nie ma wymiany ruchu sieciowego. Wykorzystywane są narzędzia do wysyłania małych fragmentów danych nagłówkowych w regularnych odstępach czasu. W konsekwencji resetowane są liczniki czasu bezczynności (timeout) a wszystkie połączenia atakującego są podtrzymywane przy życiu i obsługiwane przez serwer.
    \item Proces ten doprowadza do sytuacji, w której docelowy serwer WWW utrzymuje otwarte połączenia przez cały czas trwania ataku. W rezultacie szybko zostaje wyczerpana pula dostępnych wątków, po czym aplikacja staje się niedostępna dla żądań od uprawnionych użytkowników z zewnątrz.
\end{enumerate}

Ponieważ atak operuje na zestawionych sesjach TCP, podstawowym narzędziem obronnym jest odpowiednio krótki limit czasu na odebranie nagłówków żądania. W serwerze Nginx parametr \texttt{client\_header\_timeout} ogranicza czas transmisji całego nagłówka, a nie tylko odstęp między jego kolejnymi fragmentami; jego wartość domyślna wynosi 60~s \cite{nginx_core}. Sood i Hubballi zauważają, że atak, w którym odstęp między kolejnymi fragmentami przekracza limit czasu serwera, jest skuteczny jedynie przez część czasu trwania, ponieważ nowe żądania muszą napływać, zanim wygasną poprzednie \cite{sood2023slowtrack}. Zbyt krótki limit powoduje jednak rozłączanie legalnych użytkowników z niestabilnym i wolnym łączem, dlatego detekcja powinna uwzględniać tolerancję pozwalającą odróżnić atakującego od legalnego użytkownika, a blokowanie wyłącznie na podstawie adresu IP może objąć innych użytkowników ukrytych za tym samym adresem NAT \cite{sikora2021generator}. Z tego względu stosuje się również serwery pośredniczące (ang. reverse proxy) o architekturze sterowanej zdarzeniami, które obsługują tysiące powolnych połączeń bez dedykowania im osobnych wątków właściwego serwera aplikacji \cite{sikora2021generator}.
\subsubsection{R.U.D.Y. (Slow POST)}
R.U.D.Y. (ang. \textit{R U Dead Yet}), nazywany również Slow POST \cite{sikora2021generator}, jest bezpośrednio powiązany z wcześniej omówionym atakiem SlowLoris: również w tym przypadku dochodzi do powolnego i konsekwentnego zużywania zasobów serwera ofiary, prowadząc do niedostępności działającej usługi. Różnica między tymi wektorami ataków jest na poziomie mechaniki protokołu HTTP, R.U.D.Y wykorzystuje żądania HTTP POST stosowane m.in. do przesyłania danych w formularzach internetowych oraz przesyłania plików.

W prawidłowym żądaniu HTTP POST, w sekcji zdefiniowanych nagłówków, klient przekazuje parametr Content-Length, informujący serwer o fizycznym rozmiarze w bajtach ciała przesyłanej wiadomości. Pozwala to systemowi docelowemu na prawidłową inicjalizację strumienia bufora oczekującego na dane. Mechanizm R.U.D.Y. rozpoczyna się od poprawnego sformułowania i otwarcia połączenia aplikacyjnego z formularzem. W nagłówkach żądania POST atakujący wprowadza zawyżoną wartość dla atrybutu Content-Length, sugerując przesłanie do systemu znaczącej paczki danych rzędu megabajtów. Po poprawnym zamknięciu bloku nagłówków ciągiem "\verb|\r\n\r\n|", atak przechodzi do fazy przesyłania ciała żądania (ang. payload). Aby utrzymać aktywne połączenie z serwerem jak najdłużej, atakujący przesyła dane z niską szybkością transferu. W rezultacie, szczególnie przy użyciu sieci botnet do przeprowadzenia ataku na dużą skalę, zasoby po stronie serwera zostają skonsumowane do obsługi żądań atakującego i stają się niedostępne dla legalnych użytkowników usługi \cite{sikora2021generator}.

Podobnie jak w przypadku ataku SlowLoris, mitygacja wektora R.U.D.Y. stanowi wyzwanie dla zapór sieciowych warstw L3/L4, ponieważ złośliwy ruch opiera się na technicznie poprawnych żądaniach HTTP i w pełni zestawionych sesjach TCP. Limity czasu bezczynności mierzone między kolejnymi odczytami są skuteczne tylko wobec atakującego, który przerywa transmisję na dłużej, niż wynosi limit; atakujący przesyłający kolejny fragment danych przed jego upływem utrzymuje połączenie aktywne \cite{sikora2021generator}. W serwerze Nginx parametr \texttt{client\_body\_timeout} działa właśnie w ten sposób -- ogranicza odstęp między dwoma kolejnymi odczytami ciała żądania, a nie czas transmisji całego ciała \cite{nginx_core}.

Uzupełnieniem obrony jest buforowanie żądań przez serwer pośredniczący: przy włączonym buforowaniu, które w serwerze Nginx jest ustawieniem domyślnym, całe ciało żądania jest odbierane od klienta, zanim żądanie zostanie przekazane do serwera aplikacyjnego \cite{nginx_proxy}. Dzięki temu pula wątków roboczych aplikacji nie jest blokowana przez powolnych klientów. Sikora i in. zalecają ponadto ograniczenie czasu trwania i liczby otwartych połączeń z jednego adresu IP oraz czasu oczekiwania serwera na odebranie żądania \cite{sikora2021generator}. Alternatywą dla pojedynczych progów jest detekcja wieloparametrowa: system SlowTrack łączy liczbę niekompletnych żądań z czasem odpowiedzi, liczbą odpowiedzi i kodów statusu odczytanych z logów, liczbą przełączeń kontekstu oraz liczbą gniazd i procesów serwera, osiągając na serwerze działającym w sieci uczelnianej czułość 99,92\% przy precyzji 99,66\% w oknach 15-sekundowych \cite{sood2023slowtrack}.
\subsubsection{Slow Read i powolne ataki na HTTP/2}
Odwrotną strategię stosuje atak Slow Read: atakujący wysyła poprawne żądanie GET dotyczące większego zasobu, a następnie ustawia w nagłówku TCP bardzo małą wartość okna odbiorczego, zmuszając serwer do wysyłania odpowiedzi w niewielkich częściach \cite{sikora2021generator}. W testach Sikory i in. był to jeden z dwóch ataków skutecznych wobec serwera Nginx~1.14.0: po ustanowieniu około 1900 połączeń zasoby serwera zostały wyczerpane, a niedostępność trwała przez cały czas ataku. Autorzy wskazują, że wykrycie tego ataku wymaga sygnałów warstwy transportowej -- skrajnie małego okna TCP, prędkości transmisji danych i liczby takich połączeń -- oraz starannego doboru progu tolerancji dla legalnych, wolnych klientów \cite{sikora2021generator}.

Protokół HTTP/2 wprowadził nowe warianty powolnych ataków, wykorzystujące m.in. mechanizm kontroli przepływu, np. ogłoszenie zerowego rozmiaru okna odbiorczego. Ze względu na różnice operacyjne między HTTP/1.1 a HTTP/2 znane mechanizmy obronne przed powolnymi atakami na HTTP/1.1 nie wykrywają ataków na HTTP/2. Tripathi zaproponował wykrywanie tych ataków w czasie rzeczywistym na podstawie sekwencji zdarzeń protokołu, tj. kolejnych ramek HTTP/2 obserwowanych w trakcie trwania żądania \cite{tripathi2024delays}; metodę tę omówiono w podrozdziale~\ref{sec:ml}.
\subsubsection{HTTP/2 Rapid Reset}
Wprowadzenie standardu HTTP/2 znacząco zoptymalizowało przesyłanie zasobów webowych, głównie poprzez rozwiązanie problemu blokowania linii żądań (ang. head-of-line blocking), charakterystycznego dla protokołu HTTP/1.1. Innowacją w HTTP/2 było wdrożenie binarnego multipleksowania współbieżnych strumieni (ang. stream concurrency) \cite{rfc9113}. Pozwala ono klientowi na wysyłanie wielu niezależnych żądań i asynchroniczne odbieranie odpowiedzi w ramach pojedynczego, ciągłego połączenia TCP. W okresie od sierpnia do października 2023 roku masowo wykorzystywano podatność CVE-2023-44487, znaną jako Rapid Reset, wynikającą z właściwości samego protokołu: anulowanie żądań pozwala szybko resetować wiele strumieni \cite{nvd2023cve44487}. W odróżnieniu od ataków \textit{low-and-slow} jest to atak o wysokiej intensywności żądań, wymuszający na serwerze kosztowne przetwarzanie.
Aby zapobiec wyczerpaniu zasobów serwera, specyfikacja HTTP/2 definiuje mechanizm negocjacji za pomocą ramki SETTINGS. Ustala ona maksymalny limit jednoczesnych strumieni. Jednocześnie protokół dopuszcza możliwość przerwania zainicjowanego żądania poprzez przesłanie ramki RST\_STREAM \cite{rfc9113}. Otrzymanie takiego komunikatu obliguje serwer do przerwania przetwarzania danego strumienia i zwolnienia przydzielonych mu zasobów.

Algorytm ataku Rapid Reset polega na metodycznym nadużywaniu mechanizmu zestawiania i przerywania strumieni. W ramach pojedynczego połączenia TCP atakujący generuje setki ramek inicjujących zapytania, po czym natychmiast przesyła odpowiadające im ramki RST\_STREAM. Ponieważ zresetowane strumienie natychmiast przestają wliczać się do limitu współbieżnych strumieni określonych w parametrze SETTINGS, system obronny nie przerywa połączenia TCP. Atakujący precyzyjnie nie przekracza ustalonego progu np. 100 aktywnych zapytań w danym momencie. Serwer aplikacyjny ofiary jest zmuszony do nieustannego rezerwowania zasobów na parsowanie nowych zapytań, alokację struktur danych i natychmiastowe wykonywanie procedur ich niszczenia. Ten proces generuje potężny narzut operacyjny po stronie serwera, prowadząc do szybkiego wyczerpania zasobów CPU przy minimalnym wykorzystaniu przepustowości sieciowej przez botnet atakującego. Według raportu technicznego firmy Cloudflare ataki tego typu osiągnęły szczyt nieco ponad 201 milionów żądań na sekundę \cite{pardue2023rapidreset}.

Dodatkowo adresy IP zidentyfikowanych klientów były czasowo blokowane (mechanizm \textit{IP Jail}), co uniemożliwiało tym adresom korzystanie z HTTP/2 również w innych domenach chronionych przez dostawcę \cite{pardue2023rapidreset}.

\subsection{Wymagania wobec mechanizmów obrony}
Przegląd wektorów ataków prowadzi do trzech wymagań wobec obrony realizowanej na poziomie pojedynczego serwera. Po pierwsze, blokowanie na podstawie adresu źródłowego jest skuteczne wobec ataków bezpośrednich, o ile adresy nie są fałszowane, oraz wobec ataków warstwy aplikacyjnej, które wymagają zestawienia połączenia TCP; nie jest natomiast skuteczne wobec ataków odbiciowych, w których źródłami ruchu są reflektory (tabela~\ref{tab:taksonomia}). Po drugie, ataki \textit{low-and-slow} nie wyróżniają się wolumenem, więc ich wykrywanie wymaga sygnałów opisujących stan połączeń -- czas ich trwania, liczbę przesłanych bajtów, przekroczenia limitów czasu -- a nie wyłącznie liczby pakietów czy żądań. Po trzecie, odrzucanie ruchu z zablokowanych źródeł powinno następować możliwie wcześnie, zanim pakiet obciąży stos sieciowy systemu operacyjnego (podrozdział~\ref{sec:xdp}).

\section{Analiza stanu wiedzy o metodach obrony przed atakami DDoS}
Skala współczesnych ataków rozproszonej odmowy usługi DDoS z roku na rok osiąga rekordowe wartości. Według raportu technicznego dostawcy usług chmurowych Cloudflare największe odparte ataki w warstwie sieciowej osiągnęły 3,8 Tbps oraz 2,14 miliarda pakietów na sekundę \cite{arora2024tbps}, a ataki aplikacyjne typu HTTP/2 Rapid Reset -- ponad 201 milionów żądań na sekundę \cite{pardue2023rapidreset}. Dane dostawców należy jednak traktować jako obraz z jednego punktu obserwacji, ponieważ różne źródła pomiarowe istotnie się między sobą różnią \cite{hiesgen2024age}. Wobec takich wyzwań klasyczne, jednowymiarowe podejścia do mitygacji, opierające się wyłącznie na lokalnych zaporach sieciowych, są niewystarczające. Wymagane jest wdrożenie wielowarstwowej strategii obrony w głąb (ang. \textit{Defense in Depth}). Poniżej omówiono kolejno umiejscowienie mechanizmów obronnych, filtrowanie pakietów w jądrze systemu operacyjnego, metody detekcji oparte na uczeniu maszynowym oraz metodykę ich ewaluacji.

\subsection{Umiejscowienie obrony: sieć operatora, anycast i zapory aplikacyjne}\label{sec:umiejscowienie}
\subsubsection{Rozproszona architektura Reverse-Proxy i load balancing}
W związku ze znacznym ograniczeniem wydajności pojedynczych węzłów serwerowych oraz lokalnych zapór sieciowych, konieczna była zmiana podejścia w mitygacji ataków typu rozproszonej odmowy usługi. Kluczowe zmiany zaszły na poziomie architektury, ponieważ współczesne systemy obrony składają się z wielu instancji serwerów typu reverse-proxy z wdrożonymi mechanizmami równoważenia obciążenia (ang. load balancing) i sieci dostarczania treści CDN. Fundamentem technologicznym tego modelu jest adresacja \textit{Anycast} wspierana przez protokół BGP (Border Gateway Protocol).

\textit{Anycast} to technologia umożliwiająca przypisanie tego samego adresu IP wielu hostom, często geograficznie rozproszonym, znajdującym się w tzw. punktach obecności (ang. Points of Presence) \cite{rfc4786}. Infrastruktura sieci Internet polega na protokole BGP w celu identyfikacji optymalnych tras przesyłu danych pomiędzy systemami autonomicznymi (ang. Autonomous Systems - AS) identyfikowanymi unikalnymi numerami ASN. W klasycznym wdrożeniu Anycast każdy węzeł rozgłasza ten sam prefiks sieciowy w protokole BGP. Mechanika wyboru najlepszej ścieżki BGP, oparta z reguły na najkrótszej liczbie skoków przez systemy autonomiczne (AS Path length) oraz wartości metryk MED, powoduje, że routing w Internecie naturalnie dzieli i przekierowuje globalny ruch od klientów lub botnetów do najbliższego centrum danych udostępniającego docelowy adres IP.

Zaletą tego rozwiązania jest rozproszenie ruchu generowanego przez atakującego pomiędzy wiele lokalizacji. Operator może dodatkowo sterować podziałem ruchu między węzłami za pomocą technik inżynierii ruchu BGP -- wydłużania ścieżki AS (ang. \textit{AS-path prepending}), atrybutów społeczności czy zatruwania ścieżek -- zebranych w przygotowany zawczasu zestaw reakcji (ang. \textit{playbook}); ze względu na czas zbieżności routingu zmiany te nie powinny być wprowadzane częściej niż co 5 minut \cite{rizvi2022anycast}. Gdy pojedynczy węzeł ulega przeciążeniu lub awarii, wycofanie trasy (ang. route withdrawal) z lokalnego routera przekierowuje ruch do innych sprawnych węzłów i pozwala utrzymać dostępność usługi. Obrona na poziomie routingu działa zatem w skali minut i chroni przepustowość łączy, podczas gdy filtrowanie na poziomie hosta działa w skali sekund, lecz nie odciąży wysyconego łącza dostępowego.

Popularnym rozwiązaniem jest architektura dwustopniowa, gdzie infrastruktura brzegowa (Tier 1) działa bezstanowo, mitygując wolumetryczne ataki L3/L4 typu ICMP, UDP, SYN flood oraz ataki amplifikacyjne DNS, co zabezpiecza przepustowość dalszej komunikacji. Odfiltrowany ruch sieciowy przekazywany jest dalej do aplikacji na warstwę Tier 2, gdzie operują zapory WAF i load balancery proxy obsługujące terminację sesji TLS oraz zwalczające wektory wyczerpania zasobów, takie jak Slow POST. Detekcję i mitygację ataków wolumetrycznych można również przenieść do samej sieci: system Jaqen, zrealizowany na programowalnych przełącznikach, mitygował ataki o przepustowości 380 Gbps z czasem reakcji nieprzekraczającym 15 sekund \cite{liu2021jaqen}.

Wiodącym standardem technologicznym w implementacji warstwy Tier 2 jest oprogramowanie Nginx. Serwery Nginx buforują żądania przed przekazaniem ich do serwerów aplikacyjnych \cite{nginx_proxy}, a ich architektura sterowana zdarzeniami zapewnia odporność na ataki utrzymujące połączenia \cite{sikora2021generator}, co ułatwia dystrybucję legalnego ruchu do docelowych serwerów backendowych. Zarządzanie tym ruchem realizowane jest poprzez algorytmy równoważenia obciążenia, z których do najpowszechniej stosowanych należą:
\begin{itemize}
    \item Round Robin – domyślny mechanizm rozdzielający nadchodzące żądania sekwencyjnie i równomiernie do kolejnych serwerów w puli.
    \item Least-Connected – algorytm dynamicznie kieruje nowy ruch do węzła o najmniejszej aktualnej liczbie aktywnych połączeń. Jest on pomocny w łagodzeniu ataków typu SlowLoris, zapobiegając przeciążeniu pojedynczej instancji sztucznie przedłużanymi sesjami.
    \item IP Hash – metoda wykorzystująca funkcję skrótu obliczaną z adresu IP klienta do przypisania go do stałego serwera docelowego. Gwarantuje to zachowanie trwałości sesji w warstwie aplikacyjnej, co jest niezbędne dla poprawnego działania wielu złożonych aplikacji webowych.
\end{itemize}
\subsubsection{WAF - Web Application Firewall i odciski TLS}
Mechanizmy obronne takie jak routery brzegowe czy reguły \textit{nftables}, które operują w warstwie sieciowej oraz transportowej modelu OSI, są skuteczne w mitygacji ataków wolumetrycznych w tych warstwach, jednak nie sprawdzają się w analizie zaszyfrowanego ruchu w warstwie aplikacji L7. Botnety atakującego stosują wektory ataków takie jak HTTP GET/POST Flood, SlowLoris czy nadużywanie złożonych punktów końcowych API. W związku z asymetrią zużycia zasobów oraz ze względu na maskowanie złośliwego ruchu dynamicznymi pulami adresów proxy, skuteczna mitygacja wymaga wdrożenia specjalistycznych zapór aplikacji webowych.

Wiodącym standardem open-source w architekturze WAF jest oprogramowanie ModSecurity oraz jego nowsza implementacja w języku Go -- Coraza WAF. Rozwiązania te, integrowane jako moduły serwerów pośredniczących np. Nginx, realizują głęboką inspekcję (ang. Deep Packet Inspection -- DPI) odszyfrowanego strumienia HTTP. Fundamentem detekcji są reguły z pakietu OWASP Core Rule Set (CRS) operujące na sygnaturach znanych ataków. Chmurowe platformy WAF w większym stopniu wykorzystują analizę behawioralną: dynamicznie budują modele referencyjne (ang. baselines) dla chronionych zasobów i przypisują sesjom użytkowników współczynniki ryzyka, a zamiast bezwarunkowego blokowania mogą stosować wyzwania przeglądarkowe (ang. browser challenges), których wykonanie jest mało kosztowne dla legalnych przeglądarek, lecz obniża opłacalność ataku prowadzonego przez skrypty.

W odpowiedzi na techniki rotacji źródłowych adresów IP systemy WAF wykorzystują profilowanie klientów na podstawie przebiegu negocjacji TLS (ang. \textit{TLS fingerprinting}). Pierwszym szeroko przyjętym standardem w tej dziedzinie była metoda JA3, opracowana w firmie Salesforce przez J.~Althouse'a, J.~Atkinsona i J.~Atkinsa i udostępniona jako oprogramowanie otwarte w 2017 roku \cite{althouse2017ja3}. Metoda analizuje pakiet \textit{ClientHello}, przesyłany jawnym tekstem w początkowej fazie negocjacji szyfrowania (ang. TLS Handshake), i pobiera dziesiętne wartości bajtów pięciu pól:
\begin{itemize}
    \item wersji protokołu – określającej preferowaną przez klienta generację standardu szyfrowania np. TLS 1.2 lub TLS 1.3,
    \item listy obsługiwanych szyfrów (ang. \textit{cipher suites}) – uporządkowanego według priorytetów klienta zestawu algorytmów kryptograficznych proponowanych do wymiany kluczy i szyfrowania ruchu; kolejność tej listy jest silnym wskaźnikiem biblioteki bazowej użytej przez klienta, np. OpenSSL,
    \item listy rozszerzeń – zestawu opcjonalnych funkcji protokołu, takich jak SNI, służące do wskazania nazwy domeny, z którą klient chce się połączyć, czy ALPN, umożliwiające negocjację protokołu HTTP/2; również kolejność rozszerzeń różni się w zależności od stosu technologicznego klienta,
    \item obsługiwanych krzywych eliptycznych – wykazu krzywych akceptowanych przez klienta w procesie asymetrycznej wymiany kluczy,
    \item formatów krzywych eliptycznych – parametru definiującego sposób zapisu współrzędnych punktów na krzywej eliptycznej.
\end{itemize}
Algorytm buduje z nich pojedynczy łańcuch znaków, w którym pola oddzielone są przecinkami, a wartości wewnątrz pól – myślnikami, np. \cite{althouse2017ja3}:
\begin{equation}
    \text{769,47-53-5-10-49161-49162-49171-49172-50-56-19-4,0-10-11,23-24-25,0}
\end{equation}
Łańcuch ten jest następnie zamieniany na skrót MD5, tworząc łatwy do współdzielenia, 32-znakowy odcisk, dla powyższego przykładu równy \texttt{ada70206e40642a3e4461f35503241d5}. Rozwiązanie to umożliwiło kategoryzację oprogramowania używanego przez napastnika niezależnie od adresu IP stacji końcowej, co pozwalało łączyć rozproszone węzły botnetu pod jedną sygnaturą \cite{althouse2017ja3}.

Mechanizm GREASE (ang. \textit{Generate Random Extensions And Sustain Extensibility}), w którym klient ogłasza zarezerwowane wartości parametrów TLS w celu sprawdzenia, czy druga strona poprawnie obsługuje wartości nieznane \cite{rfc8701}, nie zmienia odcisku JA3, ponieważ metoda ta całkowicie pomija wartości GREASE \cite{althouse2017ja3}. Ograniczeniem JA3 jest natomiast to, że odcisk ma postać pojedynczego skrótu całego łańcucha: zmiana dowolnego elementu, nawet jednego szyfru, daje zupełnie inny skrót. Przykładowo, aktor skanujący Internet ze stale zmienianym pojedynczym szyfrem generował ogromną liczbę różnych odcisków JA3 \cite{althouse2023ja4}.

Odpowiedzią na to ograniczenie jest rodzina metod JA4+, opublikowana przez firmę FoxIO w 2023 roku jako następca JA3 \cite{althouse2023ja4}. Odcisk JA4 ma modułowy format \texttt{a\_b\_c}. Część \textit{a} jest czytelnym prefiksem opisującym protokół transportowy (TCP lub QUIC), wersję TLS, obecność identyfikatora SNI, liczbę zadeklarowanych szyfrów i rozszerzeń oraz pierwszą wartość ALPN. Części \textit{b} oraz \textit{c} to skrócone skróty SHA-256 odpowiednio posortowanej listy szyfrów oraz posortowanej listy rozszerzeń, uzupełnionej o algorytmy podpisu w kolejności ich wystąpienia \cite{althouse2023ja4}. Sortowanie czyni odcisk niezależnym od kolejności szyfrów i rozszerzeń, a podział na części pozwala na dopasowanie częściowe: we wspomnianym przykładzie zmieniała się wyłącznie część \textit{b}, więc aktora można było śledzić na podstawie połączenia części \textit{a} i \textit{c}. Metoda JA4 jest udostępniona na licencji BSD, natomiast pozostałe metody rodziny JA4+ -- na licencji FoxIO \cite{althouse2023ja4}. Połączenie odcisków TLS z analizą behawioralną stanowi jeden z mechanizmów neutralizacji zautomatyzowanych ataków warstwy L7; nie należy on jednak do zakresu systemu realizowanego w niniejszej pracy.

\subsection{Filtrowanie pakietów w jądrze: od Netfilter do eBPF/XDP}\label{sec:xdp}
\subsubsection{Lokalna zapora sieciowa systemu operacyjnego (iptables i nftables)}
Podstawową formą obrony na poziomie pojedynczego serwera są zapory wbudowane bezpośrednio w system operacyjny. Na maszynach z jądrem typu Linux stosowany jest framework Netfilter. Netfilter definiuje zbiór punktów zaczepienia (ang. hooks) wewnątrz stosu sieciowego jądra, które pozwalają na przechwytywanie, modyfikację i odrzucanie pakietów w trakcie ich podróży przez system. Do definiowania i zarządzania regułami sieciowymi urządzenia z przestrzeni użytkownika wykorzystywany jest program iptables, w nowszych wersjach systemu Linux program nftables.

Podsystem iptables realizuje sekwencyjne przetwarzanie pakietów w oparciu o logiczną strukturę tablic i łańcuchów. Tablice klasyfikują reguły według ich przeznaczenia funkcjonalnego:

\begin{itemize}
    \item Filter -- domyślna tablica służąca do filtrowania ruchu, podejmowanie decyzji o akceptacji lub odrzuceniu pakietu,
    \item NAT (Network Address Translation) -- odpowiedzialna za translację adresów źródłowych SNAT oraz docelowych DNAT,
    \item Mangle -- przeznaczona do modyfikacji pól w nagłówkach pakietów,
    \item Raw -- służy do konfigurowania wyjątków dla mechanizmu śledzenia połączeń (conntrack),
    \item Security -- implementuje etykiety bezpieczeństwa, wykorzystywana głównie w systemach z SELinux.
\end{itemize}

Łańcuchy stanowią punkty kontrolne w stosie sieciowym jądra systemu Linux. Wyróżnia się pięć standardowych łańcuchów wbudowanych:

\begin{itemize}
    \item PREROUTING -- analiza pakietów przychodzących przed podjęciem decyzji o routingu,
    \item INPUT -- przetwarzanie ruchu skierowanego do lokalnych procesów hosta,
    \item FORWARD -- obsługa pakietów tranzytowych, przekazywanych przez host do innych węzłów,
    \item OUTPUT -- kontrola pakietów generowanych lokalnie przez system,
    \item POSTROUTING -- modyfikacja pakietów wychodzących po procesie routingu, przed transmisją przez interfejs sieciowy.
\end{itemize}
Podstawowa obrona przed atakami DDoS przy pomocy iptables opiera się na modułach ograniczających przepływność \cite{iptables_ext}. Moduł \textit{limit} pozwala na ustanowienie uśrednionego limitu przyjmowanych pakietów z wykorzystaniem algorytmu wiadra żetonów (ang. \textit{token bucket}), np. dla zapytań ICMP echo-request, z możliwością przyjęcia krótkotrwałego przyrostu ruchu. Rozwinięciem tej koncepcji jest moduł \textit{hashlimit}, który śledzi wskaźniki dla grup połączeń, np. dla każdego źródłowego adresu IP lub całej podsieci, w ramach pojedynczej reguły. Moduł \textit{connlimit} ogranicza liczbę równoległych połączeń z jednego adresu klienta lub bloku adresów, co ma znaczenie w obronie przed atakami utrzymującymi połączenia \cite{iptables_ext}. Moduły te są wykorzystywane również w produkcyjnych systemach mitygacji \cite{majkowski2017gatebot}. Kluczowym problemem jest kalibracja limitów: w badaniu Feraudo i in. limity wyznaczone na podstawie średniego natężenia ruchu urządzenia odrzucały ponad 80\% legalnego ruchu jednego z badanych urządzeń, podczas gdy limity wyznaczone na podstawie wartości szczytowych -- poniżej 1,5\% \cite{feraudo2024mitigating}.

Fundamentalną wadą architektury iptables w kontekście współczesnych ataków DDoS jest konieczność wstępnego przetworzenia wszystkich pakietów, legalnych jak i złośliwych, przed podjęciem decyzji przez skonfigurowaną regułę o ich dalszym przeznaczeniu, co angażuje zasoby pamięciowe oraz obliczeniowe hosta. Wykorzystanie modułów operujących na stanie połączenia (ang. stateful firewalling) wymaga, aby jądro systemu alokowało pamięć i utrzymywało w tablicy mieszającej wpis o każdym aktywnym połączeniu, identyfikowanym przez 5-krotkę (tak jak we wcześniej opisanym standardzie Netflow \ref{Netflow}). Zapory stanowe są w stanie skutecznie oceniać legalność pakietów z flagą ACK w protokole TCP, co jest potrzebne by uniemożliwić techniki asymetrycznego skanowania w ramach rekonesansu. Jednakże w trakcie ataku typu TCP SYN flood podsystem \textit{conntrack} momentalnie alokuje wpisy w pamięci dla każdego sfabrykowanego połączenia. Kiedy liczba wpisów przekroczy wartość parametru jądra \texttt{nf\_conntrack\_max} \cite{kernel_conntrack}, zapora wchodzi w stan wyczerpania tablicy śledzenia (conntrack exhaustion). W tym stanie jądro zaczyna odrzucać nowe pakiety, co w konsekwencji prowadzi do zablokowania usługi z perspektywy uprawnionych klientów, czyli stanowi realizację głównego celu ataku DDoS. Aby zminimalizować to ryzyko, konieczne jest wyłączenie inspekcji stanu dla specyficznych protokołów i portów, co pozbawia możliwości zaawansowanego filtrowania kontekstowego.

Wydajność zapór programowych spada również wraz z liczbą reguł, ponieważ iptables przetwarza łańcuchy reguł sekwencyjnie. Scholz i in. zmierzyli, że iptables i nftables osiągają na pojedynczym rdzeniu co najwyżej 1,5 mln pakietów na sekundę przy niewielkiej liczbie reguł, a wydajność obu mechanizmów maleje wraz z ich przybywaniem; przy 3000 regułach iptables pięciokrotnie zwiększał opóźnienie \cite{scholz2018performance}. Stałą złożoność wyszukiwania $O(1)$ zapewniają dopiero zbiory i mapy (np. \textit{ipset} lub zbiory w nftables), w których przynależność adresu sprawdzana jest jedną operacją.

Niezależnie od szybkości samej reguły zapory programowe działają stosunkowo późno w łańcuchu przetwarzania pakietu przez jądro systemu Linux. Sam fakt dotarcia pakietu do warstwy Netfilter oznacza, że sterownik karty sieciowej musiał zgłosić przerwanie sprzętowe, a jądro musiało alokować strukturę pamięci \textit{sk\_buff} (ang. socket buffer) i skopiować metadane. Mechanizm XDP uzyskuje przewagę wydajnościową właśnie dlatego, że przetwarza pakiet przed alokacją tych struktur \cite{scholz2018performance}.
\subsubsection{eBPF - Extended Berkeley Packet Filter i XDP - eXpress Data Path}
Technologia eBPF to zaawansowany mechanizm znacząco zwiększający elastyczność i bezpieczeństwo systemu operacyjnego Linux. Stanowi ona wyizolowane środowisko uruchomieniowe wewnątrz jądra systemu, nadzorowane przez rygorystyczny weryfikator kodu (ang. \textit{eBPF verifier}). Architektura ta umożliwia dynamiczne ładowanie bezpiecznych programów kompilowanych m.in. za pomocą narzędzi Clang/LLVM bezpośrednio do przestrzeni jądra (ang. \textit{kernel space}). Rozwiązanie to eliminuje konieczność kompilacji niestandardowych modułów jądra w języku C oraz restartowania usług. Wymiana danych, metryk oraz reguł filtrowania pomiędzy jądrem a aplikacjami w przestrzeni użytkownika odbywa się z wykorzystaniem zoptymalizowanych struktur danych zwanych mapami eBPF (ang. \textit{eBPF Maps}). Najczęściej wykorzystuje się do tego celu wysokowydajne tablice asocjacyjne (\textit{BPF\_MAP\_TYPE\_HASH}) oraz statyczne tablice indeksowane (\textit{BPF\_MAP\_TYPE\_ARRAY}). Systematyczny przegląd 54 prac dotyczących zastosowań eBPF w bezpieczeństwie wskazuje medianę narzutu na poziomie 2,4\% średniego wykorzystania CPU, a jednocześnie ograniczenia wynikające z weryfikatora, który utrudnia implementację złożonych algorytmów wewnątrz jądra \cite{kostopoulos2026ebpf}.

Kluczowym rozszerzeniem technologii eBPF w kontekście mitygacji ataków DDoS jest architektura XDP (ang. \textit{eXpress Data Path}). Eliminuje ona podstawowy problem tradycyjnych zapór programowych np. iptables, jakim jest nadmierne zużycie zasobów CPU oraz pamięci RAM związane z alokacją złożonych struktur \textit{sk\_buff} dla każdego przychodzącego pakietu. XDP w konfiguracji z natywnym wsparciem sterownika sprzętowego operuje bezpośrednio w kolejce odbiorczej RX interfejsu sieciowego. Pozwala to na obejście stosu sieciowego przez przechwytywanie i inspekcję ramek natychmiast po ich odebraniu z medium fizycznego, jeszcze przed przekazaniem ich do standardowych procedur jądra.

Po szybkiej analizie zawartości pakietu przez program eBPF, mechanizm XDP zwraca jeden z predefiniowanych kodów akcji, determinujących dalszą ścieżkę routingu. W architekturach ochrony przed atakami DDoS kluczowe znaczenie mają trzy z nich:
\begin{itemize}
    \item XDP\_DROP – natychmiastowe odrzucenie pakietu na poziomie sterownika interfejsu; jest to podstawowa forma mitygacji, pozwalająca na bezstanowe zrzucanie strumieni złośliwego ruchu bez obciążania procesora operacjami w wyższych warstwach systemu,
    \item XDP\_PASS – przepuszczenie wstępnie zweryfikowanego pakietu do standardowego stosu sieciowego TCP/IP jądra systemu w celu jego dalszej obsługi przez docelowe oprogramowanie,
    \item XDP\_TX – natychmiastowe odesłanie pakietu, zwykle po uprzedniej modyfikacji jego zawartości, np. adresów MAC/IP przez ten sam interfejs sieciowy, z którego został odebrany. Mechanizm ten wykorzystywany jest powszechnie w bezstanowych mechanizmach równoważenia obciążenia (ang. \textit{load balancing}), operujących z pominięciem procesora aplikacji użytkownika.
\end{itemize}
Testy wydajnościowe (ang. \textit{benchmarks}) potwierdzają przewagę XDP nad tradycyjnymi zaporami. W pomiarach Scholza i in. filtr XDP oparty na czarnej liście adresów źródłowych przetwarzał na jednym rdzeniu do 7,2 mln pakietów na sekundę przy 90\% pakietów odrzucanych, czyli około dziesięciokrotnie więcej niż iptables i nftables \cite{scholz2018performance}. Wyniki te uzyskano na fizycznej karcie sieciowej 10 GbE, dlatego ich wartości bezwzględne nie przenoszą się bezpośrednio na interfejsy wirtualne, takie jak \textit{veth}. Hadi Salim i Bitar, porównując mechanizmy list kontroli dostępu w jądrze Linux na serwerze z procesorem Intel Xeon Gold 6230R, również uzyskali lepsze wyniki dla programów eBPF w punktach zaczepienia TC i XDP niż dla iptables i ipset; zauważyli jednak, że gdy pakiety są przekazywane dalej do stosu sieciowego, różnica między XDP a TC zanika \cite{hadisalim2021acl}.

Praktycznym przykładem wdrożenia tej architektury w skali globalnej jest system \textit{L4Drop} firmy Cloudflare, opisany w raporcie technicznym \cite{fabre2018l4drop}. Wcześniej ruch analizował automatyczny system mitygacji \textit{Gatebot}, który na podstawie próbek pakietów wdrażał reguły blokujące \cite{majkowski2017gatebot}; reguły w postaci kodu BPF, dopasowujące m.in. sygnatury p0f lub zapytania DNS, były egzekwowane przez moduł \textit{xt\_bpf} zapory iptables, a przy największych atakach przez program w przestrzeni użytkownika, pomijający częściowo jądro systemu. Nowe serwery firmy wykorzystywały karty sieciowe niekompatybilne z tym rozwiązaniem, co skłoniło do przeniesienia reguł do programów eBPF uruchamianych w punkcie XDP. Ponieważ weryfikator eBPF nie dopuszczał wówczas pętli, a reguły wymagają porównywania dowolnych fragmentów nagłówków, reguły są wbudowywane w kod programu, a ich włączanie dla poszczególnych lokalizacji odbywa się przez modyfikację skompilowanego pliku ELF tuż przed załadowaniem do jądra. Próbki odrzucanych pakietów są kopiowane do bufora pierścieniowego \textit{perf event} i odczytywane asynchronicznie przez demona w przestrzeni użytkownika. Według autorów pojedynczy serwer odrzucał w trakcie ataku ponad 8 milionów pakietów na sekundę \cite{fabre2018l4drop}.

Mechanizm XDP realizuje jedynie wydajną obsługę złośliwego ruchu sieciowego w ramach płaszczyzny danych; nie odpowiada za detekcję złośliwych pakietów. Kluczem do utrzymania wysokiej wydajności jest właściwe ustrukturyzowanie danych wewnątrz samego programu eBPF. Naiwna implementacja polegająca na sekwencyjnym, iteracyjnym sprawdzaniu długich list reguł blokujących obniża przepustowość, a pełny potencjał technologii XDP osiąga się przy zastosowaniu struktur o stałej złożoności obliczeniowej $O(1)$, takich jak mapy haszujące. Koszt aktualizacji takiej mapy z przestrzeni użytkownika jest niewielki: w pomiarach Feraudo i in. dodanie reguły trwało średnio około 4,5~$\mu$s \cite{feraudo2024mitigating}, a przegląd literatury podaje 5--20~$\mu$s na aktualizację mapy oraz 0,5--2~ms koordynacji w architekturach hybrydowych z modelem uczenia maszynowego \cite{kostopoulos2026ebpf}. Filtrowanie w punkcie XDP stanowi zatem dojrzałą i zmierzoną podstawę obrony w warstwach L3/L4, a o czasie reakcji całego systemu decyduje przede wszystkim czas detekcji, a nie czas wprowadzenia blokady.

\subsection{Uczenie maszynowe i modele sekwencyjne w detekcji DDoS}\label{sec:ml}
Kluczowym czynnikiem warunkującym implementację i ewaluację modeli ML w cyberbezpieczeństwie jest dostępność zbiorów danych odzwierciedlających współczesne wzorce ataków w ruchu sieciowym. Często wykorzystywane są repozytoria takie jak CIC-IDS2017, UNSW-NB15 czy dedykowany atakom DDoS zbiór CICDDoS2019, opracowany przez Canadian Institute for Cybersecurity i obejmujący kilkanaście typów ataków opartych na protokołach TCP i UDP \cite{karrakchou2025collaborative}. Przegląd 89 publicznych zbiorów danych wskazuje jednak, że nawet najpopularniejszy z nich, CIC-IDS2017, był wykorzystywany jedynie w 29\% analizowanych prac \cite{goldschmidt2025network}. W procesie ekstrakcji cech modele zasilane są metadanymi z przepływów sieciowych, takimi jak:
\begin{itemize}
    \item entropia źródłowych adresów IP,
    \item proporcje flag kontrolnych TCP, w szczególności nienaturalny stosunek pakietów SYN do ACK,
    \item wariancja rozmiaru przesyłanych pakietów,
    \item częstotliwość zapytań z pojedynczego węzła,
    \item średni czas trwania przepływu.
\end{itemize}

W ewaluacjach prowadzonych w obrębie jednego zbioru danych klasyfikatory, takie jak drzewa decyzyjne, Random Forest czy XGBoost, osiągają bardzo wysokie wyniki -- współczynnik korelacji Matthewsa (MCC) rzędu 99\%. Cantone i in. wykazali jednak, że po przeniesieniu modelu na inny zbiór danych średni MCC spada do kilkudziesięciu procent, a w eksperymentach z selekcją cech -- z 83,86\% do 14,91\% \cite{cantone2024machine}. Wysokie wyniki raportowane dla pojedynczych zbiorów danych nie świadczą więc o skuteczności w rzeczywistym ruchu sieciowym (podrozdział~\ref{sec:metodyka}).

Klasyczne modele pozostają jednocześnie wymagającym punktem odniesienia. Drzewa decyzyjne i Random Forest osiągnęły w badaniu Almaraz-Rivery i in. najlepsze wyniki we wszystkich trzech wariantach zbioru cech, wyprzedzając modele głębokie (RNN, LSTM, GRU, MLP), a drzewo decyzyjne klasyfikowało około 30 tys. przepływów na sekundę wobec niespełna 3 tys. dla sieci GRU \cite{almarazrivera2022transport}. W detekcji ataków \textit{low-and-slow} skuteczne okazują się z kolei reguły i drzewa decyzyjne zbudowane na parametrach behawioralnych serwera, a nie na statystykach pojedynczych przepływów \cite{sood2023slowtrack}.

Klasyczne modele analizują jednak każdą obserwację niezależnie, podczas gdy ataki o niskim wolumenie rozwijają się w czasie. Problem ten adresują rekurencyjne sieci neuronowe (ang. \textit{Recurrent Neural Networks}). Sieci LSTM (ang. \textit{Long Short-Term Memory}) dzięki komórce pamięci i mechanizmowi bramek pozwalają utrzymywać kontekst w długich sekwencjach danych \cite{hochreiter1997long}, a sieci GRU (ang. \textit{Gated Recurrent Unit}) realizują podobną funkcję prostszą strukturą z bramkami aktualizacji i resetu \cite{cho2014learning}. Raportowane wyniki należy jednak interpretować ostrożnie. We wspomnianym badaniu Almaraz-Rivery i in. sieć GRU osiągnęła 99,862\% dokładności przy zbiorze cech zawierającym znaczniki czasu, lecz 96,23\% po ich usunięciu, podczas gdy drzewo decyzyjne utraciło jedynie około 0,06 punktu procentowego; modele rekurencyjne przetwarzały przy tym sekwencje o długości 1, a więc nie wykorzystywały zależności między kolejnymi przepływami \cite{almarazrivera2022transport}. Kierunkiem rozwijanym równolegle jest głębokie uczenie ze wzmacnianiem, w tym algorytm TD3 (\textit{Twin Delayed Deep Deterministic Policy Gradient}) połączony z selekcją cech wspieraną metodą SHAP \cite{satpathy2025cloud}.

Dla ataków \textit{low-and-slow} szczególnie istotny jest wybór jednostki sekwencji. Tripathi zaproponował wykrywanie powolnych ataków na HTTP/2 w czasie rzeczywistym na podstawie sekwencji zdarzeń protokołu, tj. kolejnych ramek HTTP/2 wymienianych w ramach połączenia. Model normalnego zachowania budowany jest wyłącznie z ruchu legalnego jako zbiór par zdarzeń występujących po sobie w oknie o zadanej długości, a każda sekwencja oceniana jest po każdym kolejnym zdarzeniu, co pozwala sklasyfikować żądanie przed jego zakończeniem. Na serwerze uczelnianym obsługującym rzeczywisty ruch studentów metoda osiągnęła czułość 100\% przy odsetku fałszywych alarmów 1,71--1,83\%, wykrywała wszystkie anomalne sekwencje w czasie poniżej około 30~s, a obciążenie procesora pozostawało przez większość czasu poniżej około 7\% \cite{tripathi2024delays}. Autor zbudował własne środowisko pomiarowe, ponieważ nie istniał publiczny zbiór danych z jawnym ruchem HTTP/2 \cite{tripathi2024delays}.

Zasadniczym ograniczeniem architektur RNN jest wysoki koszt obliczeniowy procesu wnioskowania. Lekka sieć konwolucyjna LUCID, operująca na oknach czasowych przepływów, klasyfikowała ponad 55 tys. próbek na sekundę, czyli ponad 40-krotnie więcej niż model złożony z warstw LSTM przy porównywalnej wartości miary F1 \cite{doriguzzicorin2020lucid}. Narzut opóźnień ogranicza bezpośrednie zastosowanie modeli rekurencyjnych na urządzeniach brzegowych obsługujących ruch o dużej przepływności. Rozwiązaniem tej asymetrii może być integracja programowalnych płaszczyzn danych w języku P4 z architekturą sieci definiowanych programowo (ang. \textit{Software-Defined Networking}) oraz sieciami z wczesnym wyjściem (ang. \textit{Early-Exit Neural Networks}) \cite{karrakchou2025collaborative}. Architektura ta dzieli proces decyzyjny na dwie domeny:
\begin{itemize}
    \item Płaszczyzna danych (ang. \textit{Data Plane}): przełącznik P4 oblicza w rejestrach 28 cech przepływu inspirowanych narzędziem CICFlowMeter (m.in. długości nagłówków, odstępy czasowe między pakietami, liczniki flag TCP), skwantyzowanych do 8 bitów, i klasyfikuje je skwantyzowaną (INT8) jednowymiarową siecią konwolucyjną. Przy wystarczającej pewności decyzja zapada już na przełączniku (\textit{early exit}).
    \item Płaszczyzna kontroli (ang. \textit{Control Plane}): kontroler SDN jest angażowany wyłącznie wtedy, gdy model na przełączniku zwróci wynik o niskiej pewności (ang. \textit{confidence score}). Mapy cech niejednoznacznych przepływów trafiają do kontrolera, gdzie decyzję podejmuje model GRU, a kontroler instaluje odpowiednie reguły przepuszczające lub blokujące.
\end{itemize}

W symulacji w środowisku NS-3 obie ścieżki decyzyjne osiągnęły wartości miary F1 równe 99,91\% i 99,90\%, a przepustowość legalnego ruchu została zachowana podczas obu symulowanych ataków \cite{karrakchou2025collaborative}. Wynik ten uzyskano jednak przy łączach o przepustowości 1,5~Mb/s, więc nie dowodzi on skuteczności przy rzeczywistych przepływnościach. Uzupełnieniem tego obrazu jest przegląd zastosowań eBPF: ograniczenia weryfikatora powodują, że jedynie 2 z 11 prac wykorzystujących uczenie maszynowe realizowały wnioskowanie wewnątrz jądra \cite{kostopoulos2026ebpf}. Uzasadnia to architekturę, w której model działa w przestrzeni użytkownika, a decyzje są egzekwowane przez program XDP -- przyjętą w niniejszej pracy.

W niniejszej pracy model rekurencyjny GRU jest rozwijany jako eksperymentalny komponent płaszczyzny sterowania i oceniany względem reguł deterministycznych, co odpowiada zaleceniu porównywania modeli uczonych z prostymi punktami odniesienia \cite{arp2022dos}. Przegląd literatury wskazuje cztery otwarte kompromisy projektowe. Po pierwsze, jednostka sekwencji: zakończone żądania odczytywane z logów serwera albo zdarzenia obserwowane w trakcie trwania połączenia -- wykrywanie powolnych ataków HTTP/2 w czasie rzeczywistym opiera się na sekwencjach zdarzeń protokołu rejestrowanych, zanim żądanie zostanie zakończone \cite{tripathi2024delays}. Po drugie, sposób uczenia: model nadzorowany na znanych rodzinach ataków albo model normalnego zachowania uczony wyłącznie na ruchu legalnym \cite{tripathi2024delays}. Po trzecie, koszt wnioskowania: modele rekurencyjne przetwarzają o rząd wielkości mniej próbek na sekundę niż sieci konwolucyjne i drzewa decyzyjne \cite{doriguzzicorin2020lucid,almarazrivera2022transport}. Po czwarte, współpraca z heurystykami: wieloparametrowe reguły behawioralne osiągają wysoką czułość dla ataku Slowloris na serwerze działającym w sieci uczelnianej \cite{sood2023slowtrack}, dlatego model sekwencyjny musi wnosić informację, której reguły nie mają.

\subsection{Metodyka ewaluacji, środowiska testowe i pułapki}\label{sec:metodyka}
Arp i in. przeanalizowali 30 prac z czołowych konferencji bezpieczeństwa z ostatnich dziesięciu lat i zidentyfikowali dziesięć typowych błędów metodycznych w stosowaniu uczenia maszynowego, od stronniczości próby (ang. \textit{sampling bias}) po ewaluację wyłącznie w warunkach laboratoryjnych (ang. \textit{lab-only evaluation}); stronniczość próby i podglądanie danych testowych (ang. \textit{data snooping}) występowały co najmniej częściowo odpowiednio w 90\% i 73\% prac \cite{arp2022dos}. W studium przypadku detekcji botnetu Mirai prosty detektor oparty na liczbie pakietów w 10-sekundowym oknie i rozstępie międzykwartylowym osiągnął czułość 0,996 przy odsetku fałszywych alarmów 0,001, wobec 0,882 dla złożonego zespołu autoenkoderów Kitsune \cite{arp2022dos}. Wynika z tego, że każdy model uczony powinien być porównywany z prostym, deterministycznym punktem odniesienia, a wyniki raportowane jako czułość przy ustalonym, niskim odsetku fałszywych alarmów.

Druga grupa problemów dotyczy uogólniania. W badaniu Cantone i in. modele trenowane na zbiorach CIC-IDS2017 i CSE-CIC-IDS2018, obejmujących m.in. klasy ataków Slowloris i Slowhttptest, traciły większość skuteczności po przeniesieniu na drugi zbiór, ponieważ etykiety dawały się oddzielić wartościami charakterystycznymi dla danego zbioru, a pojedyncza cecha pozwalała uzyskać 69,7\% MCC w obrębie zbioru. Autorzy konkludują, że trening na jednym publicznym zbiorze danych nie wystarcza do zbudowania odpornego systemu wykrywania włamań \cite{cantone2024machine}.

Goldschmidt i Chudá w przeglądzie 89 zbiorów danych wskazują, że jedynie co piąty zbiór zawiera rzeczywisty ruch sieciowy, a łączenie zbiorów pochodzących z różnych sieci i okresów jest błędne z założenia, ponieważ wprowadza obciążenie wynikające z odmiennych wzorców ruchu. Zalecają podział danych zgodny z czasem (dane treningowe sprzed danych ewaluacyjnych), ewaluację na wielu zbiorach i w wielu powtórzeniach oraz stosowanie testów istotności statystycznej \cite{goldschmidt2025network}.

Większość badań opiera się przy tym na środowiskach laboratoryjnych: w przeglądzie zastosowań eBPF w bezpieczeństwie od 81,4\% do 87\% prac (autorzy podają obie wartości) ewaluowano wyłącznie w środowisku testowym, z wykorzystaniem syntetycznych generatorów ruchu zamiast obciążeń produkcyjnych \cite{kostopoulos2026ebpf}. Wzorcem są prace łączące środowisko laboratoryjne z ewaluacją na działającym serwerze, jak w przypadku metody Tripathiego \cite{tripathi2024delays} oraz systemu SlowTrack, ocenianego m.in. w 48-godzinnym eksperymencie na serwerze uczelnianym z atakującym umieszczonym w chmurze obliczeniowej \cite{sood2023slowtrack}. Do generowania ruchu wykorzystuje się wyspecjalizowane narzędzia: generator powolnych ataków Sikory i in. \cite{sikora2021generator} oraz, dla ruchu o dużej przepływności, generator MoonGen, osiągający 14,88 mln pakietów na sekundę na jednym rdzeniu \cite{emmerich2015moongen}. Przykładem znaczenia opisanych zaleceń jest praca, w której hybrydowy model GRU-NTM uczony na połączeniu dwóch różnych zbiorów danych (ruch normalny z jednego, ataki z drugiego) nie popełnił ani jednego błędu klasyfikacji, przy braku testów w czasie rzeczywistym \cite{panggabean2024intelligent}; tak uzyskany wynik świadczy o rozdzielności zbiorów danych, a nie o skuteczności w rzeczywistym ruchu.
\section{Wnioski z przeanalizowanych przykładów}
Z przeglądu stanu wiedzy wynikają następujące wnioski, stanowiące punkt wyjścia dla projektowanego rozwiązania:
\begin{enumerate}
    \item Filtrowanie pakietów w punkcie XDP jest dojrzałą i zmierzoną metodą obrony na poziomie hosta, istotnie wydajniejszą od zapór opartych na Netfilter. Jej ograniczeniami są ataki odbiciowe, w których adresy źródłowe należą do reflektorów, oraz ataki wysycające łącze dostępowe, którym pojedynczy host nie może przeciwdziałać.
    \item Wykrywanie ataków \textit{low-and-slow} opiera się w literaturze na sygnałach stanu połączeń i serwera oraz na sekwencjach zdarzeń protokołu, a nie na wolumenie ruchu. Proste progi liczby połączeń można ominąć, a skuteczność samego ataku zależy od architektury i limitów czasu serwera.
    \item Wśród przeanalizowanych prac opublikowane, otwarcie dostępne dowody przewagi modeli rekurencyjnych w wykrywaniu powolnych ataków HTTP są nieliczne: badania porównawcze często nie wykorzystują zależności sekwencyjnych, a najlepiej udokumentowane podejście sekwencyjne nie jest siecią neuronową.
    \item Wiarygodna ewaluacja wymaga prostych punktów odniesienia, kontrolowanego generowania danych w jednym środowisku, wielokrotnych powtórzeń z testami istotności oraz, w miarę możliwości, weryfikacji na rzeczywistym ruchu.
    \item W konsekwencji proponowane rozwiązanie łączy egzekwowanie blokad w punkcie XDP z deterministycznymi heurystykami w płaszczyźnie sterowania oraz eksperymentalnym modelem sekwencyjnym GRU, ocenianym względem tych heurystyk zgodnie z powyższymi zasadami.
\end{enumerate}
\section{Koncepcja rozwiązania problemu wykrycia i mitygacji ataków DDoS}
Proponowane rozwiązanie opiera się na hybrydowej architekturze dzielącej system ochrony na dwie ściśle współpracujące płaszczyzny: płaszczyznę sterowania (\textit{Control Plane}) działającą w przestrzeni użytkownika (\textit{User Space}) oraz płaszczyznę danych (\textit{Data Path}) osadzoną bezpośrednio w przestrzeni jądra systemu operacyjnego (\textit{Kernel Space}). Podział ten pozwala na elastyczną realizację zaawansowanej analityki behawioralnej przy jednoczesnym zachowaniu maksymalnej wydajności podczas niskopoziomowej filtracji pakietów.

Płaszczyzna sterowania odpowiada za wykrywanie anomalii w ruchu sieciowym w warstwie aplikacji L7. Przychodzący ruch jest w pierwszej kolejności kierowany przez serwer reverse proxy Nginx, który pośredniczy w dostępie do aplikacji www oraz odpowiada za zakańczanie połączeń szyfrowanych (\textit{TLS Offloading}). Serwer proxy generuje logi dostępowe w formacie JSON, które są na bieżąco strumieniowane do skryptu integracyjnego w języku Python. Skrypt realizuje mechanizm przesuwnego okna czasowego, wyodrębnia kluczowe metryki żądań i przekazuje je do predykcyjnej sieci neuronowej GRU (\textit{Gated Recurrent Unit}) zaimplementowanej w środowisku PyTorch. Model uczenia maszynowego analizuje sekwencje zdarzeń w celu identyfikacji korelacji czasowych, charakterystycznych dla ataków typu \textit{low-and-slow}.

W momencie wykrycia anomalii płaszczyzna sterowania uruchamia procedurę mitygacyjną. W przestrzeni użytkownika demon Python wysyła sygnał przerwania aktywnych połączeń sieciowych w ramach sesji TCP, które obciążają serwer. Równolegle złośliwt adres IP jest dynamicznie wstrzykiwany przy użyciu biblioteki \textit{bcc} do współdzielonej mapy eBPF o strukturze \textit{BPF\_MAP\_TYPE\_HASH}, która jest łącznikiem z płaszczyzną danych. Niskopoziomowy program XDP uruchomiony na poziomie sterownika wirtualnej karty sieciowej weryfikuje każdy napływający pakiet IPv4 pod kątem obecności na czarnej liście w stałym czasie $O(1)$. Ruch pochodzący ze zidentyfikowanych adresów botnetu jest natychmiast odrzucany przy użyciu akcji \textit{XDP\_DROP}. Dzięki temu eliminacja złośliwych pakietów następuje na samym brzegu systemu operacyjnego, całkowicie pomijając kosztowny proces alokacji struktur \textit{sk\_buff} w jądrze, co minimalizuje narzut na procesor i skutecznie zapobiega wyczerpaniu zasobów serwera.

\subsection{Architektura}
Proof of Concept (PoC) w środowisku zwirtualizowanym, z wykorzystaniem wirtualnej maszyny z systemem Linux Ubuntu oraz wirtualnych interfejsów sieciowych veth. System detekcji oraz mitygacji można podzielić ze względu na dwie płaszczyzny:
\begin{itemize}
    \item Płaszczyzna Danych - Główny silnik filtrujący oparty na mapach eBPF i XDP, który operuje bezpośrednio na sterowniku karty sieciowej.   
    \begin{itemize}
        \item Ekstrakcja cech: Program XDP czyta surowe nagłówki pakietu np. z krotki 5-tuple: źródłowe/docelowe IP, porty, protokół, natychmiast po jego odebraniu w karcie sieciowej, pomijając kosztowny w zasoby proces alokacji struktur \textit{sk\_buff} w systemie operacyjnym.
        \item Struktury Map: Zoptymalizowane struktury tablic przechowujące zablokowane adresy IP węzłów botentu, takie jak \textit{BPF\_MAP\_TYPE\_HASH}, współdzielone z przestrzenią użytkownika. Gwarantuje to stały czas operacyjny wyszukiwania na poziomie $O(1)$.
        \item Decyzja na poziomie sprzętu: Po sprawdzeniu mapy, kod XDP zgłasza jeden z wyników wyjścia dla pakietu: \textit{XDP\_DROP} - odrzucenie złośliwego pakietu na samym brzegu karty sieciowej bez obciążenia CPU, lub \textit{XDP\_PASS} - przepuszczenie pakietu do standardowego stosu TCP/IP jądra Linuksa. 
        \item Zbieranie telemetrii: Kod inkrementuje liczniki odrzuconych pakietów bezpośrednio w mapach eBPF, umożliwiając bezinwazyjny odczyt statystyk w czasie rzeczywistym przez systemy nadrzędne.
    \end{itemize}
    \item Płaszczyzna Sterowania - Odpowiedzialna za detekcję ataków DDoS. Gdy nastąpi detekcja nowych złośliwych adresów, informacja jest dynamicznie przekazywana do płaszczyzny danych.
    \begin{itemize}
        \item Reverse Proxy: Izoluje bezpośredni dostęp do serwera aplikacyjnego i odpowiada za zakańczanie połączeń TLS (SSL Offloading), co zdejmuje obciążenie kryptograficzne z serwera plikacyjnego. Generuje ustrukturyzowane logi dostępowe w formacie JSON, które są na bieżąco strumieniowane do modułu ML.
        \item Model uczenia maszynowego: Predykcyjna sieć neuronowa oparta na architekturze GRU (ang. Gated Recurrent Unit). Analizuje zrekonstruowane sekwencje logów aplikacyjnych w przesuwnych oknach czasowych. Jej celem jest odnalezienie ukrytych korelacji czasowych, charakterystycznych dla ataków wyczerpujących zasoby w warstwie aplikacji.
        \item Demon integrujący: Aplikacja Python pośrednicząca i stanowiąca most między płaszczyznami. W przypadku wykrycia złośliwego IP przez model GRU, demon wykonuje dwie równoległe akcje mitygacyjne: dynamicznie wstrzykuje adres do mapy eBPF, co skutkuje natychmiastowym odrzucaniem nowych żądań przez XDP oraz wysyła sygnał przerwania w celu zniszczenia aktywnych, wiszących sesji TCP obciążających serwer aplikacyjny.
    \end{itemize}
\end{itemize}

\subsection{Komponenty zastosowane w projekcie}
\begin{itemize}
    \item Środowisko sieciowe i generator ruchu: Dwie odizolowane logicznie przestrzenie nazw sieciowych (\textit{attacker\_ns} oraz \textit{server\_ns}) połączone parą wirtualnych interfejsów (\textit{veth\_attacker} i \textit{veth\_server}). Przestrzeń atakującego pozwala na generowanie sekwencji żądań HTTP o niskiej częstotliwości, symulujących zachowanie botnetu w atakach typu low-and-slow.
    
    \item Filtr płaszczyzny danych XDP/eBPF: Program niskopoziomowy w języku C \textit{xdp\_ddos\_filter.c} uruchamiany bezpośrednio na poziomie sterownika wirtualnej karty sieciowej. Odpowiada za natychmiastową ekstrakcję źródłowego adresu IP z nagłówków pakietów IPv4, weryfikację jego obecności w mapie blokad oraz wykonywanie akcji \textit{XDP\_DROP} - odrzucenie przed alokacją struktur jądra \textit{sk\_buff}, lub \textit{XDP\_PASS} - przepuszczenie pakietu do stosu TCP/IP hosta.
    
    \item Współdzielona struktura tablic eBPF Map: Zoptymalizowana mapa typu \\\textit{BPF\_MAP\_TYPE\_HASH} o nazwie \textit{blacklist\_map}, stanowiąca most pamięciowy pomiędzy przestrzenią jądra a przestrzenią użytkownika. Przechowuje zablokowane adresy IP oraz liczniki telemetrii odrzuconego ruchu, gwarantując czas wyszukiwania na poziomie $O(1)$.
    
    \item Serwer odwrotnego proxy Nginx: Komponent odpowiedzialny za zakańczanie połączeń szyfrowanych  oraz izolację właściwego serwera aplikacyjnego. Konfiguracja serwera wymusza generowanie ustrukturyzowanych logów dostępowych w formacie JSON, zawierających kluczowe metryki czasowo-rozmiarowe żądań dla modelu uczenia maszynowego.
    
    \item Model uczenia maszynowego GRU: Predykcyjna, głęboka sieć rekurencyjna zaimplementowana w bibliotece PyTorch. Model analizuje sekwencje logów sieciowych w przesuwnych oknach czasowych na podstawie trzech wyekstrahowanych cech: czasu trwania żądania, rozmiaru nagłówków oraz liczby przesłanych bajtów, klasyfikując sesje jako anomalie lub ruch prawidłowy.
    
    \item Demon integrujący w przestrzeni użytkownika: Skrypt zarządzający \textit{control\_plane.py} napisany w języku Python z wykorzystaniem biblioteki \textit{bcc}. Odpowiada za dynamiczną kompilację i załadowanie kodu XDP, asynchroniczne strumieniowanie logów z serwera Nginx, podawanie cech na wejście modelu GRU oraz realizację dwutorowej mitygacji (wstrzykiwanie IP do mapy eBPF oraz natychmiastowe zrywanie sesji TCP za pomocą narzędzia \textit{ss}).
\end{itemize}

MODEL_PATH = "training_results/gru_ddos_model.pth"

def ip_to_network_bytes(ip_str):
    return struct.unpack("=I", socket.inet_aton(ip_str))[0]


def block_ip_in_xdp(ip_str):
    ip_int = ip_to_network_bytes(ip_str)
    blacklist_map[blacklist_map.Key(ip_int)] = blacklist_map.Leaf(0)
    print(f"[XDP] BLOCKED IP: {ip_str}. Rule is active on hardware.")


def kill_zombie_connections(ip_str):
    try:
        subprocess.run(["ss", "-K", "dst", ip_str], check=True, capture_output=True)
        print(f"[OS] Killed hanging TCP sessions for address {ip_str}.")
    except subprocess.CalledProcessError as e:
        print(f"[-] Error while killing sessions for {ip_str}: {e.stderr.decode().strip()}")
    except FileNotFoundError:
        print("[-] The 'ss' tool is not installed (iproute2 package).")


def tail_nginx_logs(file_path):
    with open(file_path, 'r') as f:
        f.seek(0, os.SEEK_END)
        while True:
            line = f.readline()
            if not line:
                time.sleep(0.05)
                continue
            yield line


client_sequences = defaultdict(lambda: deque(maxlen=SEQUENCE_LENGTH))
banned_ips = set()

try:
    print("[*] Starting Nginx -> GRU -> XDP integration...")
    print(f"[*] Listening for logs in file: {NGINX_LOG_FILE}")

    for log_line in tail_nginx_logs(NGINX_LOG_FILE):
        try:
            log_data = json.loads(log_line)
            client_ip = log_data.get("client_ip")

            if client_ip in banned_ips:
                continue

            features = [
                float(log_data.get("request_time", 0.0)) * 1000000,
                float(log_data.get("request_length", 0)),
                float(log_data.get("bytes_sent", 0))
            ]

            client_sequences[client_ip].append(features)

            if len(client_sequences[client_ip]) == SEQUENCE_LENGTH:
                raw_sequence = np.array(list(client_sequences[client_ip]))
                scaled_sequence = scaler.transform(raw_sequence)
                tensor_seq = torch.tensor([scaled_sequence], dtype=torch.float32).to(device)

                with torch.no_grad():
                    logits = gru_model(tensor_seq)
                    probability = torch.sigmoid(logits).item()

                if probability > PREDICTION_THRESHOLD:
                    print(f"\n[GRU] DETECTED L7 ATTACK (Slowloris/DoS) - IP: {client_ip} | Confidence: {probability * 100:.1f}%")
                    block_ip_in_xdp(client_ip)
                    kill_zombie_connections(client_ip)
                    banned_ips.add(client_ip)
                    del client_sequences[client_ip]

        except json.JSONDecodeError:
            continue
        except Exception as e:
            print(f"[-] Loop error: {e}")

except KeyboardInterrupt:
    print("\n[*] Execution interrupted by user. Cleaning up environment...")
finally:
    bpf.remove_xdp(INTERFACE, 0)
    print(f"[+] XDP program detached from {INTERFACE}. Finished.")

import torch
import torch.nn as nn


class GRUDDoSClassifier(nn.Module):
    """
    Gated Recurrent Unit (GRU) classifier designed for DDoS attack detection.
    
    """

    def __init__(self, input_size, hidden_size, num_layers, output_size=1, dropout_rate=0.2):
        """
        Initializes the GRUDDoSClassifier model.

        Parameters:
        -----------
        input_size : int
            The number of expected features in the input x (e.g., request time, length, bytes sent).
        hidden_size : int
            The number of features in the hidden state h of the GRU layer.
        num_layers : int
            Number of recurrent layers stacked on top of each other (Deep RNN).
        output_size : int, optional
            The number of output units. Defaults to 1 for binary classification.
        dropout_rate : float, optional
            The dropout probability for regularization between GRU layers. Defaults to 0.2.
        """
        super(GRUDDoSClassifier, self).__init__()

        self.hidden_size = hidden_size
        self.num_layers = num_layers

        self.gru = nn.GRU(
            input_size=input_size,
            hidden_size=hidden_size,
            num_layers=num_layers,
            batch_first=True,
            dropout=dropout_rate if num_layers > 1 else 0
        )

        self.dropout = nn.Dropout(dropout_rate)
        self.fc = nn.Linear(hidden_size, output_size)

    def forward(self, x):
        """
        Performs the forward pass of the model.

        Parameters:
        -----------
        x : torch.Tensor
            Input tensor of shape (batch_size, sequence_length, input_size).

        Returns:
        --------
        torch.Tensor
            Output logits of shape (batch_size, output_size).
        """
        h0 = torch.zeros(self.num_layers, x.size(0), self.hidden_size).to(x.device)

        out, _hidden = self.gru(x, h0)
        out = out[:, -1, :]
        out = self.dropout(out)
        out = self.fc(out)

        return out

    if time_col:
        sort_cols.append(time_col)

    'Bwd Packets Length Total'

joblib.dump(scaler, SCALER_SAVE_PATH)

class DynamicDDoSDataset(Dataset):
    """
    Dataset class for dynamically generating time-series sequences from network traffic data.
    """
    def __init__(self, data, labels, seq_length):
        """
        Initializes the dynamic dataset.

        Parameters:
        -----------
        data : numpy.ndarray
            The scaled feature array.
        labels : numpy.ndarray
            The binary target labels.
        seq_length : int
            The number of time steps in each sequence.
        """
        self.data = data
        self.labels = labels
        self.seq_length = seq_length

    def __len__(self):
        """
        Returns the total number of available sequences.
        """
        return len(self.data) - self.seq_length

    def __getitem__(self, idx):
        """
        Generates one sequence slice and its corresponding label on the fly.
        """
        x_seq = self.data[idx : (idx + self.seq_length)]
        y_label = self.labels[idx + self.seq_length - 1]
        return torch.tensor(x_seq, dtype=torch.float32), torch.tensor([y_label], dtype=torch.float32)


print("[*] Generating dynamic loader...")
dataset = DynamicDDoSDataset(features_scaled, labels, SEQUENCE_LENGTH)
dataloader = DataLoader(dataset, batch_size=BATCH_SIZE, shuffle=True)

model = GRUDDoSClassifier(input_size=INPUT_SIZE, hidden_size=HIDDEN_SIZE, num_layers=NUM_LAYERS).to(device)
criterion = nn.BCEWithLogitsLoss()
optimizer = optim.Adam(model.parameters(), lr=0.001)

print("[*] Starting training process...")
for _epoch in range(EPOCHS):
    model.train()
    total_loss = 0
    for batch_X, batch_y in dataloader:
        batch_X, batch_y = batch_X.to(device), batch_y.to(device)

        optimizer.zero_grad()
        outputs = model(batch_X)
        loss = criterion(outputs, batch_y)
        loss.backward()
        optimizer.step()

        total_loss += loss.item()

    avg_loss = total_loss / len(dataloader)
    print(f"Epoch [{_epoch + 1}/{EPOCHS}], Loss: {avg_loss:.4f}")

torch.save(model.state_dict(), MODEL_SAVE_PATH)
print(f"[+] Model successfully saved to {MODEL_SAVE_PATH}")
print(f"[+] Scaler successfully saved to {SCALER_SAVE_PATH}")

#include <uapi/linux/bpf.h>
#include <uapi/linux/if_ether.h>
#include <uapi/linux/ip.h>
#include <uapi/linux/in.h>

BPF_HASH(blacklist_map, u32, u64, 100000);

int xdp_ddos_mitigation(struct xdp_md *ctx) {
    void *data_end = (void *)(long)ctx->data_end;
    void *data     = (void *)(long)ctx->data;

    struct ethhdr *eth = data;

    if ((void *)(eth + 1) > data_end) {
        return XDP_PASS;
    }

    if (eth->h_proto != bpf_htons(ETH_P_IP)) {
        return XDP_PASS;
    }

    struct iphdr *ip = data + sizeof(*eth);

    if ((void *)(ip + 1) > data_end) {
        return XDP_PASS;
    }

    u32 src_ip = ip->saddr;

    u64 *drop_counter = blacklist_map.lookup(&src_ip);

    if (drop_counter) {
        lock_xadd(drop_counter, 1);
        return XDP_DROP;
    }

    return XDP_PASS;
}
